# 调度配置阻断修复

范围：用户批准修复已有界面的单位补录、策略草稿配置同步与只读试算。不启用策略、不下发 PCS、不发送通知。
基线为 `51c8bfa` / `v0.8.8` / Schema 062；本修复收为 `v0.8.9`，Schema 不变。实际部署状态以发布记录为准。

## 根因与修复

1. 现场 SOC / PCS 的 L0、L1、L2 单位都未声明，并非页面读取时丢失。旧“直接使用”和当前加工编辑入口锁住单位，缺少正常维护路径。
   - 原始数值点无单位时，L1 可明确声明真实工程单位，不改变数值。
   - 已有实体可在“标准实体 → 模板与版本 → 编辑当前加工”补录单位，再检查、发布。
   - 保留 L0 原值、L2 身份、历史、已有控制限值与写点；失败时整笔事务回滚。
   - 已知单位不能直接改标；非数值、跨节点 L2 不能这样补单位；空白单位不能进入已发布合同。
   - 控制占用、未结束命令、其他活动 L1 的直接引用或 selector/formula 依赖会阻止改动。
2. 旧策略配置基线为 699，现场配置已到 714；保存仍沿用旧基线，试算因配置不一致被阻断。
   - 显式“保存草稿”在配置共享锁与策略 CAS 下重新核对实体，采用当前配置基线。
   - 同实体历史绑定缺少单位时可补齐；已知类型或单位漂移仍拒绝，改字段名、顺序或方向不能绕过。
   - 保留 JDM、全部绑定和新鲜度；不修改原发布版本、启用状态或故障锁。
3. 仓储层将超龄 GOOD 先覆盖为 STALE，遮蔽实际超时原因。
   - 保留已存质量，由统一校验区分 `L2_INPUT_STALE`、时间戳缺失与非 GOOD 质量。
   - 仍 fail closed，不延长 10 秒阈值，不将旧数据当新数据。

- 本机真实接口无头主干 7/7，55.265 秒；包括旧实体补录单位后身份和值不变、单位再次变为只读。
- 完整后端 629 项：387 通过、242 条件跳过；跳过项不计入通过，真实 PG 验证另列如上。

新鲜度另有未修复问题：只读配置确认实际发布主题，22.113 秒内收到 574 包，PCS、SOC
目标各 22 次，约每秒到达；同期 L0/帧仍约 5～6 秒提交。瓶颈已收窄到应用单未完成帧门禁下的
`complete()` 终态事务及提交可见性，具体慢在哪条 SQL 仍需分段计时。`finished_at` 在该事务开始前生成，
