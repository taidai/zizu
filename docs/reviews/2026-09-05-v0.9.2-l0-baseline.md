# v0.9.2：缩小事务 B 的 L0 基线读取

## 问题与改动

v0.9.1 已减少发布时第二遍 L0 整理，但事务 B 推进 latest 之前仍会读取并转换所有旧点位。现场只读分析显示约 2,000 行基线整理存在明显 Python 对象转换开销。

本次只缩小这一次读取：读取本帧处理快照涉及的点位，以及从上一终态帧到当前拍号刚跨过 STALE 边界的点位。SQL 先筛选，之后才做 UUID、原始值和质量转换。

使用内部 `L0PublicationBaseline` 显式区分“没有上一终态帧”和“有上一帧，但候选集合为空”，避免空增量误变成全量发布。成功、失败与预算超限处理共用该入口。没有修改 Schema、API、质量期限、配置栅栏、原始值类型、单写者或提交后可见语义，也没有引入缓存。

## 本轮验证

- 先运行真实 PostgreSQL `PostgresFrameRepository.complete` 回归用例：1 个更新点加 1,800 个旧点，原实现物化 1,802 行，断言失败；修复后最多 2 行，断言通过。该计数证明减少不必要工作，不代表现场整体延迟的同比降幅。
- 真实 PostgreSQL 专项组合 57 项通过：发布增量、首帧、空增量、新点、过期与复活、原始类型、失败回滚、租约恢复、来源证据和实时流。
- 完整交付检查中的后端单元、脚本、前端 106 项测试、生产构建均退出 0。条件 PostgreSQL 跳过项不作为数据库通过证据；数据库证据来自上一条单独运行。
- 构建保留已有大包警告；后端测试有依赖弃用警告和预期故障注入日志。本轮没有新增依赖。
- 独立只读代码审查未发现 Critical / Important 问题；审查不替代测试。
- 本机隔离运行实例无头主干 7/7，通过约 51.8 秒；覆盖节点 CRUD、导入、原始实时/历史、加工发布与模板生命周期、实体来源以及告警选择。临时资源按用例清理，不涉及真实 PCS。
