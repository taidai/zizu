# 数据帧发布路径：最小性能修复

状态：**局部修复已随v0.9.0发布；现场主干7/7通过，但5分钟性能门槛和10秒数据新鲜度仍未达标。** 发布证据见[1号机v0.9.0记录](../deploy-1号机-v0.9.0-http.md)。

基线为 v0.8.9 / `008f7f51439d745056fa7e3a563e1e5276b86ecf`，Schema062 不变。没有更换架构、增加依赖或修改同步提交、节拍、新鲜度和控制门禁。

## 已证实的问题

现场18.361秒只读采样中，两项调度输入的最大数据年龄为15.318秒；149次检查中108次超过10秒。该窗口只完成2帧，不能把它解释为所有时段的平均吞吐。

对生成帧通知的原始 SELECT 做只读 EXPLAIN ANALYZE：返回5条L2结果，却在历史基线关联中每个实体平均过滤约4万条记录。查询已经有索引，但执行计划选择按提交序倒序扫描并过滤实体。不能把它笼统归因于“没有索引”或“JSON太大”。

同一只读、可重复读快照对比：

| 指标 | 原查询 | 修复查询 |
| --- | ---: | ---: |
| 执行时间 | 366.808毫秒 | 2.140毫秒 |
| 共享数据页命中 | 22,488 | 21 |
| 返回实体数 | 5 | 5 |

原有19个结果字段逐项相同，包含值、质量、时间、来源摘要及加工修订。这个微观查询结果**不等于整帧提速比例**，也不能证明10秒新鲜度已达标。现场没有应用修复代码。

## 修复方式

事务B本来就先写L2历史、推进L2 latest，再生成不可变outbox。生成当前帧通知时直接使用该事务已经计算好的latest保留值与原GOOD时间；质量、原因、当前观测和来源证据仍取该帧历史事实。

读取必须同时匹配实体、事件和帧号。缺失或错配抛出 `DATA_FRAME_L2_LATEST_MISMATCH`，整个事务回滚，不借用未来帧、不制造正常值。显式重建历史帧保留原有历史查询路径；正常消费者仍只读提交后的不可变payload。

同时修复一个边界：旧GOOD历史已按保留期清理时，BAD帧的通知不能丢掉latest仍正确保留的旧值及其真实时间。`false`不能被当作空值。

## 尚未完成

现场仍存在WAL写入/落盘等待及其他阶段耗时。只读采样中的磁盘等待随窗口变化，尚不足以证明唯一原因。未放宽10秒门槛、丢弃新观测、关闭同步提交或启动多个未完成帧；没有新增索引、改数据库参数、清理业务数据或重启现场依赖。

v0.9.0已发布并完成现场复验：主干562.811秒；发布后轻量16秒年龄测量最高13.344秒，64项检查33项超过10秒。下一步围绕每帧两次全量L0整理和其余事务CPU耗时做最小优化，保持原始类型、质量转STALE、来源及提交后可见语义；不得把本次单查询结果写成“数据帧性能问题全部修复”。

## 补充分段测量

第二个16.072秒只读窗口仍只完成2帧，135次年龄检查中85次超过10秒，最大14.235秒。但该窗口未观察到显著COMMIT等待；“读取上一帧L0”之后多次处于 idle in transaction，表示数据库等待客户端继续，而不是SQL仍在执行。不能沿用“全部是磁盘慢”的结论。

在独立只读诊断进程、同一可重复读快照中对比旧版与修复版的通知组装：旧版2.378秒、修复版1.308秒，最终payload完全相同。两次均读取1,849条L0两遍并输出5条L2；修复版整理L0行约0.962秒，UUID构造11,114次。测量含cProfile开销，只代表该子过程，不是主服务完整事务或最终吞吐。

另一次5.238秒进程CPU差分：Neuron约89%、后端约81%、桌面登录程序约36%（均按单核100%计）。这是负载观察，不能证明哪一个进程是唯一根因。未停进程、修改资源限额或加入跨帧缓存；保留这一瓶颈线索，先验收已验证的查询改动。
