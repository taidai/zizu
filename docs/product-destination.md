# ZiZu 产品目的地

## 产品定位

ZiZu 是面向工业控制系统交付的开源物联网低代码平台。首要使用者是系统集成商和实施工程师；他们通过配置完成项目交付，业主操作员使用交付后的系统进行日常运行。

## 开发目标

将 ZiZu 建设为一个以“节点树及其 L0—L2 数据主干”为核心、通过简单配置即可交付光储充 EMS 及工业控制系统的配置型 IoT 平台：节点树负责组织站点、光伏、储能、充电、负荷及设备的真实物理归属，L0 原始点位承载 Neuron、Modbus、MQTT、OPC UA 等协议采集数据，L1 点位加工以可复用、不可变版本完成品牌字段映射、单位换算、枚举与故障码解析、多点组合、跨节点 L2 计算、质量与时间处理以及强类型安全公式，L2 全局实体形成具有稳定业务名称、类型、单位、实时值、质量、时间戳和来源证据的标准业务接口，告警、策略、控制、画面和报表只能引用 L2 全局实体，不得直接依赖品牌 L0 点位；内部以强类型关系模型保存节点、原始点位目录、点位加工模板与修订、实体定义与实例、来源绑定、独立控制动作、站点配置版本、安装计划、命令及审计，以两张全平台共享的 TimescaleDB hypertable 分别保存 L0 原始历史和 L2 业务历史，并以两张最新值表提供实时快照，L1 只保存版本化配置而不重复保存中间计算结果，L2 历史必须携带加工修订、站点配置版本和 L0 来源证据；产品界面以物理节点树作为统一入口，向业主操作员提供站点实时能流、光伏/储能/充电/负荷状态、SOC、设备可用性、活动告警和数据质量，并支持按节点下钻 L2 实时值、历史趋势、来源证据和消费者，向实施工程师提供 L0 点位管理、L1 点位加工模板选择与匹配、L2 全局实体预览、变更计划、阻断项处理、原子应用和机器验收，历史分析在统一时间轴联动功率、SOC、电量、告警、策略、控制和质量事件并标记加工版本变化；完整数据流为“协议网关采集 → L0 历史与最新值持久化 → 固定 L1 加工修订计算 → 同一事务写入 L2 历史与最新值 → 事务提交后通过认证 WebSocket 推送 → 告警、策略、控制、画面和报表消费”，数据库失败不得推送虚假更新，乱序数据不得倒退最新值，BAD 或 STALE 数据不得冒充有效实时值，控制必须经过范围限制、联锁、确认、持久命令、回读和审计，配置变更必须先形成 `add`、`update`、`preserve`、`delete_candidate` 和 `block` 计划，存在阻断时保持零运行写入，最终使实施工程师无需修改源码、编写 SQL 或 JSON/YAML，也无需接触 UUID、寄存器地址和品牌标签 ID，只需建立节点树、填写必要通信参数、选择已支持的设备与点位加工模板、处理少量歧义并执行安装验收，即可完成可追溯、可升级、可回滚、可验证的工业系统交付。

“简单配置”只适用于协议驱动、设备品牌型号和点位加工模板已经存在的场景。新协议、新品牌或新设备型号的首次接入属于平台模板开发，不得伪装成普通站点配置。实施工程师仍需填写设备 IP、端口、从站号、接入凭据等必要连接参数；寄存器地址、标签 ID、换算公式、内部 UUID 和数据库结构应封装在受版本控制的模板及平台内部。

## 节点树及其 L0—L2 数据主干

节点树表达真实物理拓扑和业务归属，L0、L1、L2 是挂载在所选节点上的数据视角，而不是伪装成物理子节点的树层级：

```text
物理节点树：站点 → 能源子系统 → 设备
                  │
                  ├─ L0 原始点位：协议采集事实
                  ├─ L1 点位加工：品牌适配、换算、组合、质量与时间处理
                  └─ L2 全局实体：稳定业务语义、实时值、历史值与来源证据
                                      │
                                      ├─ EMS 运行工作台
                                      ├─ 告警与历史分析
                                      ├─ 自动策略
                                      └─ 统一控制命令
```

必须满足以下不变量：

- 节点树只保存身份、父子关系、类型和配置版本，不保存实时值；
- 同一设备内的 L1 加工可以读取本节点 L0 原始点位；
- 跨节点计算只能组合已经标准化的 L2 全局实体，禁止跨节点直接引用品牌 L0 点位；
- 每个 L2 全局实体只归属一个物理节点；跨节点派生实体归属能够完整解释其业务范围的最低共同上级节点；
- L2 全局实体由实体定义和实体实例构成：定义表达跨品牌复用语义，实例表达站点内稳定运行对象；
- 更换设备品牌或升级点位加工修订时，L2 实体实例身份及上层引用保持稳定，只改变经过计划审查的来源绑定；
- 告警、策略、控制、画面和报表不得绕过 L2 全局实体直接读取 L0 或 L1；
- 可控制实体的写入动作必须独立声明，禁止从读取换算公式反向推导现场写入。

## 目标数据结构

目标结构采用“配置关系表 + L0/L2 时序表 + 事件与证据表”，不为每个节点、设备或点位创建独立 hypertable，也不以自由 JSON/EAV 代替核心约束。

### 配置与模型

- 节点：站点、父节点、稳定节点键、节点类型、显示名称和拓扑深度；
- L0 原始点位目录：所属节点、稳定源键、协议适配器、地址引用、数据类型、单位和读写能力；
- L1 点位加工：模板、不可变修订、强类型输入、输出实体定义、表达式、质量策略、新鲜度、时间策略和控制资格声明；
- L2 全局实体：实体定义、实体实例、确认来源绑定、当前加工修订及其生效站点配置版本；
- 控制动作：动作键、输入类型、单位、上下限、变化率、风险等级、确认策略、分派适配器和回读实体；
- 交付治理：解决方案包、站点配置版本、安装计划、安装结果、发布锁定和不可变审计。

内部使用 UUID 建立外键和幂等关系；实施工程师使用站点内稳定的节点键、实体键和可读名称，界面不得要求复制内部 UUID。

### 实时与历史

主要时序存储固定为：

- 一张共享 L0 历史 hypertable，保存原始点位观测；
- 一张 L0 最新值表，供点位诊断和 L1 计算读取；
- 一张共享 L2 历史 hypertable，按稳定实体实例保存业务观测；
- 一张 L2 最新值表，供 REST 首屏快照和运行读取；
- L2 连续聚合，供分钟、小时和长期历史查询。

L2 历史至少保存业务观测时间、实体实例、强类型值、质量及原因、来源观测时间、平台计算时间、点位加工修订、站点配置版本、来源引用和去重摘要。数值、布尔、字符串和多码状态使用强类型列；每条记录只能有一种值表示。旧时间样本可以进入历史，但不得倒退最新值。数据库只有在 L2 历史插入与最新值更新同一事务提交成功后，才能发布 WebSocket 增量。

L1 默认不持久化每个中间计算结果；L0 原始事实、L2 业务事实、点位加工修订和来源证据应足以重放与审计。高频录波、电能质量波形等数据形态使用独立专用时序结构或对象存储，不挤入普通遥测 hypertable。

## 首个参考交付

光储充 EMS 是首个参考交付。达到交付就绪至少包括：

- 设备接入；
- 实时监控；
- 历史数据；
- 分级告警；
- 手动与自动控制；
- 基础能源策略；
- 操作审计；
- 部署与运维。

计费、工单、移动端和多租户不属于首版参考交付。

## 配置式交付验收

在协议驱动、设备品牌型号和点位加工模板已经存在的前提下，新站点应满足：

- 无需修改 ZiZu 平台源码；
- 交付主流程不超过“建立节点树、填写连接与选择模板、自动匹配与预览、处理阻断、安装与验收”五个阶段；
- 已支持模板所需的 L0 原始点位自动匹配率至少达到 95%，其余缺失、歧义、单位或类型冲突形成可解释阻断；
- 小型光储充参考站在连接条件准备完成后，一小时内完成配置和机器验收；
- 标准生产站在一个工程日内完成配置，不修改代码、不直接操作数据库；
- 更换同类不同品牌设备后，只调整连接和点位加工模板，L2 实体、告警、策略、控制语义和画面引用保持稳定；
- 交付结果通过可重复执行的自动验收和现场验收。

## 解决方案包

配置式交付以版本化解决方案包为单位，而不是逐个复制零散模板。光储充 EMS 解决方案包组合：

- 节点结构与参数契约；
- 设备模板；
- 实体定义与绑定规则；
- 告警等级、条件与故障码；
- 控制策略与输入输出映射；
- 运行页面配置；
- 机器可执行验收清单。

站点配置只实例化现场参数和实际设备映射，不复制平台代码，也不携带凭据。

解决方案包采用可进入 Git 版本控制的声明式目录，而不是数据库备份。根目录包含解决方案清单，资产使用 YAML/JSON 表达，并必须支持：

- Schema 校验；
- 包版本与平台兼容范围；
- 安装前差异预览；
- 幂等安装；
- 可审计升级。

解决方案包通过参数契约描述现场差异。参数必须声明名称、类型、单位、必填性、默认值、允许范围和是否敏感。实施工程师通过安装向导填写；敏感参数只保存运行时 Secret 引用，不进入解决方案包、站点导出或交付报告。

升级使用三方差异：旧解决方案包、当前站点配置、新解决方案包。升级前展示新增、删除、变更和冲突；站点覆盖与人工绑定默认保留，冲突必须由实施工程师明确处理，禁止静默覆盖。

## EMS 运行工作台

首版不建设通用拖拽大屏设计器。光储充 EMS 提供固定的运行工作台，解决方案包只配置：

- 导航入口；
- 设备与能源子系统分组；
- 关键指标及其实体引用；
- 趋势图实体集合与默认时间范围；
- 告警和控制入口的可见性。

布局组件库和允许的页面结构由平台版本控制，避免解决方案包携带任意前端代码。

产品界面至少包含：

- 物理节点树：站点、光伏、储能、充电、负荷、并网点和设备的真实拓扑；
- 实时能流：光伏出力、储能充放电、电网购售电、充电功率、园区负荷和功率平衡；
- 运行状态：SOC、SOH、设备可用性、运行模式、活动告警、数据质量和数据年龄；
- 节点下钻：运行人员默认查看 L2 全局实体的实时值、历史、来源摘要和消费者；工程人员可继续查看 L1 点位加工与 L0 原始点位；
- 历史分析：功率、SOC、电量、运行状态、告警、策略、控制及质量事件共享时间轴，质量空洞不补线，并标记加工修订变化；
- 配置向导：节点树、连接参数、模板选择、自动匹配、L2 预览、变更计划、阻断处理、原子应用和验收报告；
- 控制工作台：显示命令来源、限值、联锁、确认、下发、回读和审计，不以写接口 HTTP 成功代替现场完成。

运行首页不得退化为点位表或通用 IoT 仪表盘。L0/L1/L2 是节点的工程下钻视角，站点能流、设备状态和运行约束是光储充 EMS 的第一视觉层级。

实施工程师的默认交付界面采用“引导式交付驾驶舱”：顶部固定展示建立节点树、连接与模板、自动匹配与预览、处理阻断、安装与验收五个阶段；左侧展示物理节点树及各节点完整性；中部围绕所选节点展示 L0 原始点位、L1 点位加工、L2 全局实体的数据主干预览以及 `add`、`update`、`preserve`、`delete_candidate`、`block` 安装计划；右侧只展示需要人工处理的阻断、下一动作和机器验收进度。存在阻断时安装按钮必须禁用；阻断解决后重新计算并固定计划摘要，才能进入原子安装和机器验收。交付驾驶舱与业主操作员的 EMS 运行工作台是两个明确界面：前者用于配置和验收，后者用于能流、状态、告警、历史和授权控制，禁止把工程配置直接暴露为运行首页。

## 站点与控制边界

首版采用单实例单站。数据结构可以保留未来引入 `site_id` 的演进空间，但多租户和跨站管理不进入首版。

ZiZu 定位为站级 EMS/SCADA 配置、监控和协调控制平面，不替代 PCS、BMS、充电桩、保护装置或 PLC 中的毫秒级闭环、过压过流过温保护、急停、安全联锁、通信失效安全状态及 SIL 相关功能。平台失联或命令超时时，现场设备必须依靠本地控制和保护进入已定义的安全状态。

所有操作员手动控制和自动策略控制统一产生控制命令，并经过同一入口执行权限、限值、联锁、幂等、冷却时间、审计和写后回读。页面、规则或其他模块不得绕过该入口直接写设备。

发生竞争时，控制优先级固定为“设备本地保护与急停 > 现场人工控制 > 调度或站级安全约束 > EMS 自动策略 > 普通计划任务”。平台必须显式保存命令来源、目标动作、设定值、有效期、优先级、幂等键和策略证据，低优先级来源不得静默覆盖高优先级或仍有效的命令。

控制命令状态至少包括：已受理、校验通过、已下发、回读确认；终止状态包括拒绝、超时、失败和结果不一致。写接口返回成功不代表控制完成，只有回读确认满足命令声明的期望值、容差和超时才算成功。

## 实体与绑定

实体模型分为实体定义和实体实例。实体定义表达跨设备复用的标准语义；实体实例表达站点内实际对象的运行语义。规则、EMS 运行工作台、告警和控制统一引用实体实例 ID。

解决方案包声明实例槽位，站点参数决定实例数量与标识。安装或升级阶段必须为必需实体实例形成确定性绑定：

- 唯一候选可进入待确认或按包内明确规则自动确认；
- 零候选视为缺失；
- 多候选视为歧义；
- 缺失和歧义均阻止交付就绪；
- 运行时禁止按优先级或创建顺序静默选择数据源。

若需要主备数据源，应由显式故障切换策略表达，不复用歧义绑定机制。

## 告警语义

告警由现场观测驱动，统一状态至少包括：正常、待触发、活动未确认、活动已确认和已恢复。告警定义支持持续时间、迟滞、恢复条件和通知节流。

确认只表示业主操作员已经知悉活动告警，不改变现场状态；恢复只由现场恢复条件产生，人工不能直接把仍在发生的故障标记为恢复。MQTT、标签和实体告警作为来源适配器进入同一告警状态接口，不再各自维护不同的状态语义。

## 交付报告

解决方案包的验收清单至少自动检查：

- 设备与协议网关在线；
- 必需实体绑定完整且无歧义；
- 实时数据新鲜；
- 告警能够触发、确认和按现场条件恢复；
- 控制命令成功写入并完成回读；
- 基础策略可以仿真且输入完整；
- 操作产生完整审计记录。

光储充参考交付还必须证明：

- L0 原始观测、L1 加工结果和 L2 全局实体的值、单位、质量、时间戳及来源证据一致；
- REST 最新值、WebSocket 增量和数据库 L2 最新值一致，重启后历史与配置版本仍可读取；
- 功率、SOC、电量、质量空洞和加工修订在历史分析中可解释；
- 越权控制、越限设定、联锁不满足和失效确认均稳定拒绝且零现场写入；
- 手动控制和自动策略都经过统一命令入口，并获得匹配目标、容差和超时的现场回读；
- 设备品牌替换试验不要求修改 L2 引用的告警、策略、控制语义和运行页面。

验收运行生成带解决方案包版本、站点配置版本、执行时间和逐项证据的交付报告。

## 身份与权限

首版定义三种运行角色：

- `admin`：平台安装、解决方案包生命周期、系统配置和用户管理；
- `engineer`：设备、实体绑定、告警、策略配置和交付验收；
- `operator`：运行监控、告警确认和被授权的控制命令。

高风险控制在角色权限之上继续使用命令级策略，并可要求二次确认。所有权限必须由服务端校验，页面可见性不构成安全边界。

生产模式默认要求所有业务 REST API 和 WebSocket 完成认证，仅最小存活探针允许匿名访问。开发模式可以显式开启匿名访问，但运行状态和界面必须醒目标记为不安全；不得通过缺省配置隐式进入匿名模式。

## 发布与回滚

平台发布固定版本的多架构容器镜像并提供内容摘要；解决方案包独立使用语义版本。每次部署形成发布锁定，至少记录：

- 平台版本；
- 容器镜像 digest；
- 数据库 Schema/迁移版本；
- 解决方案包版本；
- 站点配置版本。

部署、升级和回滚只能使用可验证的不可变制品，不使用 `latest` 或宿主机源码覆盖作为正式交付方式。

## 四小时交付试验

配置式交付目标通过独立交付试验证明：由未参与 ZiZu 开发的实施工程师，在干净备用环境和模拟或真实协议设备上从零计时。全过程只允许使用公开文档、发布制品、解决方案包以及产品界面和公开 API。

出现以下任一情况即判定该次配置式交付失败：

- 修改平台源码；
- 直接操作数据库或执行临时 SQL；
- 使用未包含在公开交付流程中的一次性脚本；
- 依赖开发人员口头指导才能完成；
- 完整独立交付试验超过四小时；
- 连接条件准备完成后，小型光储充参考站的五阶段配置与机器验收超过一小时；
- 已支持模板所需 L0 原始点位的自动匹配率低于 95%；
- 机器验收清单未全部通过。

## 开源边界

公开仓库包含平台核心、设备模板格式、光储充 EMS 参考配置、部署方案和验收测试。

具体客户参数、访问凭据、现场实际拓扑和商业服务不得进入公开仓库。

## Wayfinder 的目的地

形成一份可实施、可验收的 ZiZu 产品规格，明确配置资产模型、参考交付流程、运行安全边界、开源边界以及从当前 v0.4.77 到交付就绪版本的实现顺序。随后将规格拆分为带依赖关系的 tracer-bullet 实现票据。
