# ADR-0005：实体实例注册表与确定性绑定接口

## Status

Accepted — 2026-08-13

维护者已确认本文的接口与测试缝；票据 06 仍需等待票据 05 的安装计划与参数契约
主缝完成。

## Context

v0.4.77 的 `t_entities` 保存 `pcs.activePower` 一类全局业务语义，实质上是实体
定义，却被 API、规则、告警和控制当作站点运行对象。`t_entity_bindings` 允许一个
实体拥有多个启用点位，`entity_resolver.py` 按 `priority`、`created_at` 排序并静默
选择第一条；规则上下文也只比较最小优先级。同优先级多候选、创建顺序变化或多台
同类设备会让运行、告警和控制引用错误的现场对象。

解决方案包需要从一个设备实例槽位生成站点内实际对象，为每个必需业务语义建立
稳定实体实例，并在交付前把它绑定到唯一现场来源。候选发现属于安装计划；运行期
不得再猜测来源。

## Decision

### 1. 领域身份

- 现有 `t_entities` 在兼容期明确解释为**实体定义**，例如
  `pcs.activePower`；定义保存数据类型、单位、读写方向和设备类别，不代表某台设备。
- **设备实例**表示站点内实际对象，例如 `PCS-01`。
- **实体实例**表示一个设备实例对实体定义的实例化，例如
  `PCS-01.activePower`。规则、告警、控制、工作台和验收最终都引用实体实例 ID。
- **实体实例槽位**属于解决方案包，声明设备类别、数量参数、稳定实例键规则、必需
  实体定义和候选匹配器。

实体实例 ID 在首次成功安装时持久生成；升级通过
`solution_installation_id + slot_id + instance_key + definition_id` 找回并保留同一 ID。
显示名、设备序号展示方式和点位名称变化都不能改变 ID。`instance_key` 来自强类型
站点参数或包内稳定序号，不从显示名推导。

### 2. 深模块接口

新增 `EntityInstanceRegistry`。安装侧与运行侧只使用三个公开操作：

```python
class EntityInstanceRegistry:
    def plan(self, request: PlanEntityInstances) -> EntityInstancePlan: ...
    def apply(self, command: ApplyEntityInstancePlan) -> ApplyOutcome: ...
    def resolve(self, entity_instance_id: UUID) -> ResolvedEntitySource: ...
```

- `plan` 接收已验证的解决方案包摘要、槽位、站点参数、当前站点配置版本和只读现场
  来源目录，返回实例新增/保留/冲突及逐实体绑定判定；不写运行配置。
- `apply` 只接受仍匹配当前包摘要、站点配置版本和来源目录版本的已批准计划。任何
  过期或阻断计划零写入；重复应用同一计划幂等。
- `resolve` 只返回实体实例的已确认主来源及其语义元数据。未绑定、停用或来源失效
  使用稳定机器码失败，绝不回退到定义名、优先级、创建时间或查询顺序。

候选 Adapter 只负责把 Neuron/点位目录规范化成来源描述；它不能创建确认绑定，也
不能参与运行期选源。

### 3. 计划判定与阻断码

每个候选必须携带匹配器稳定 ID、匹配理由、来源设备范围、点位引用、数据类型、
单位和读写方向。匹配器只使用包内声明的确定条件，例如设备实例键、模板资产 ID、
规范化点位名或协议地址模式；禁止以优先级、创建时间或数据库返回顺序破除歧义。

首版计划状态与机器码为：

- 唯一且兼容：`ready` / `ENTITY_BINDING_READY`，在计划中预选并显示理由；
- 无候选：`blocked` / `ENTITY_BINDING_MISSING`；
- 多候选：`blocked` / `ENTITY_BINDING_AMBIGUOUS`；
- 数据类型不兼容：`blocked` / `ENTITY_BINDING_TYPE_MISMATCH`；
- 单位或量纲不兼容：`blocked` / `ENTITY_BINDING_UNIT_MISMATCH`；
- 读写方向不兼容：`blocked` / `ENTITY_BINDING_DIRECTION_MISMATCH`；
- 计划依据已变化：`stale` / `ENTITY_BINDING_PLAN_STALE`。

实施工程师可以在多个候选中明确选择一个并重新生成计划；选择动作记录主体、时间、
候选理由和计划摘要。它不是在运行态调整“优先级”。

### 4. 持久化不变量

采用 expand–migrate–contract：

- 新增设备实例、实体实例和实体实例确认绑定；候选与匹配理由属于不可变安装计划
  证据，不作为运行期绑定表。
- 一个活动实体实例只能有一个确认主绑定，由数据库唯一约束和事务共同保证。
- 绑定只保存 `tag_id`；节点、协议地址和数据类型从受约束的来源目录解析，避免
  `tag_id + node_id` 两份身份漂移。
- 首版一个活动物理点位不能同时成为两个活动实体实例的主绑定。确需复用时应声明
  一个派生/虚拟实体关系，而不是复制物理绑定。
- 运行读取、告警和控制得到的均是同一 `ResolvedEntitySource`；其结果包含实体实例、
  实体定义、设备实例、确认绑定、点位来源和确认审计 ID。
- 数据新鲜度与质量属于交付/运行 readiness，不改变绑定唯一性；陈旧数据明确失败，
  不自动切到另一个候选。主备切换以后由显式故障切换策略承担。

### 5. 兼容迁移

票据 06 只建立一台设备的实例主缝：由解决方案包槽位生成设备实例和读实体实例，
通过公开安装计划解决唯一绑定，再从实体实例 API 读取实时值并写入交付报告。

旧 `t_entities` 和 `t_entity_bindings` 在 expand 阶段继续服务未迁移消费者，但新实体
实例路径不双写旧绑定，也不调用旧 `resolve_entity_binding()`。迁移预览仅把能在明确
设备范围内唯一归属的旧绑定列为候选；零候选、多候选或跨设备共享均要求人工处理。
票据 07 按规则、告警、控制和工作台逐批迁移消费者；contract 阶段删除静默优先级
选源，并把旧绑定改为只读兼容。

## Test seam to confirm

开始票据 06 的 TDD 前，请维护者确认两个公开测试缝：

1. **辅助实体缝**：从 `EntityInstanceRegistry.plan()`、`apply()` 和 `resolve()` 断言
   公开计划项、机器码、稳定 ID、幂等结果与唯一来源；使用固定来源目录 Adapter，
   不断言 SQL、私有匹配函数或内部调用次数。
2. **主交付缝的实体切片**：通过公开 API 导入带单设备槽位和一个读实体定义的固定
   解决方案包，填写站点参数，查看/批准/执行计划，协议模拟器发布数据，实体实例
   API 返回值，最终机器验收报告证明绑定完整、唯一且数据新鲜；测试不直连数据库。

首轮用例至少证明：

- 同一计划重复执行不重复创建设备、实体实例或绑定，实体实例 ID 保持不变；
- 零候选和多候选分别返回稳定阻断码且站点零变更；
- 唯一候选显示可解释理由，类型、单位和方向任一不兼容都会阻断；
- 显示名修改和来源查询顺序变化不改变实例 ID 或确认来源；
- 未确认绑定的 `resolve` 明确失败，同优先级旧绑定不能成为回退来源；
- 计划生成后来源目录变化使应用失败为 `ENTITY_BINDING_PLAN_STALE`；
- 主报告在绑定缺失、歧义或数据陈旧时不能标记交付就绪。

不新增属性测试依赖；首版使用 pytest 参数化、固定 UUID/时钟和内存 Adapter。

## Consequences

- 多设备运行对象与可复用语义分离，告警和控制获得稳定且不串设备的引用。
- 安装计划必须保存候选证据和版本，票据 06 不能绕过票据 05 单独做 CRUD 页面。
- 现有消费者需要分批迁移，兼容期会同时存在定义 API、旧全局实体路径和新实例
  路径，但新路径不会继承静默优先级选源。
- 首版禁止物理点位隐式复用和自动主备切换，减少灵活性，换取可审查、可验收的
  确定性；以后只能通过显式派生关系或故障切换策略扩展。
