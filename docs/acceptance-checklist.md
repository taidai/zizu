# ZiZu 验收清单

只有自动检查和本轮涉及的人工业务检查都取得证据，才能说“本轮完成”。

## 自动检查

- [ ] 后端完整单元测试退出码为 0；条件跳过的 PostgreSQL 测试必须如实保留为 skipped。
- [ ] `scripts` 完整测试退出码为 0。
- [ ] 前端全部 `*.test.mjs` 通过。
- [ ] 前端生产构建 `npm run build` 成功。
- [ ] 节点管理改动默认运行 Playwright 无头主干，结果为 0 失败且总耗时低于 5 分钟。
- [ ] 调度策略改动运行快速 Playwright 无头流程，完成“绑定 L2 → 试算 → 发布 → 启用 → 回读 → 停用”。
- [ ] 原始标量测试确认数字 `0/1/2`、布尔值和字符串不被测试工具互相转换。
- [ ] 提供站点地址时，首页和匿名存活接口均为 HTTP 200，运行版本与仓库 `VERSION` 一致。
- [ ] 报告记录 Git commit、平台版本、最新 Schema 和各检查结果。

运行：

```powershell
python scripts/verify_delivery.py --site-url http://zizu-host:9000
```

没有可访问站点时可省略 `--site-url`；结果必须是 `INCOMPLETE`，不能冒充通过。

节点管理无头验收在 `frontend` 目录运行：

```powershell
npm run test:e2e:node
npm run test:e2e:dispatch-strategy
```

站点地址、登录凭据、本次运行 ID 和写入确认只通过 `ZIZU_E2E_*` 环境变量传入，不得写入命令、仓库或报告。测试只能在 `E2E验证` 根节点下创建带运行 ID 的临时资源，不启用规则、不执行控制，结束后必须完成清理。失败证据保存在 `frontend/test-results/`。

## 人工业务闭环

- [ ] 使用 Browser 登录目标站点，并沿“节点树 → L0 原始点位 → L1 点位加工 → L2 全局实体 → 告警”逐页操作；不能只检查首页或存活接口。
- [ ] 节点可以新增、修改、删除，刷新后结果保持一致。
- [ ] 可以从 Neuron 预览并确认导入点位，不产生重复或错误归属。
- [ ] 所选设备的 L0 实时值、质量、时间和来源正确；能按单点查询历史。
- [ ] Neuron BIT 点位在 L0 显示协议类型 `BIT`，原值 `0/1/2` 均原样可见；`2` 标为无效并说明超出 `0/1` 范围，不能改写为布尔值。
- [ ] L0 可维护显示名称、批量启用、批量停用和批量永久删除；停用保留点位与历史，删除必须二次确认并在同一事务清除点位、实时值、历史值和采集去重记录。
- [ ] 已被 L1 加工或控制配置引用的 L0 不允许永久删除，并明确提示改用停用；未被引用的错误导入点位可删除。
- [ ] 当前 L1 正在引用的 L0 不允许直接停用，并明确提示先调整点位加工；未被引用的 L0 可停用并恢复。
- [ ] 可以在全局实体内选择一个或多个 L0，定义直接映射或强类型公式，试算失败时禁止发布。
- [ ] BIT 点位默认使用“0/1 转布尔”，明确选择 `1` 或 `0` 表示 `true`；原值 `0/1` 分别产生确定布尔值，原值 `2` 时 L2 显示当前不可用并保留上次正常值。
- [ ] 可以在“标准实体 → 数据来源与计算”查看当前加工，编辑并发布本节点新修订；管理员可创建共享模板新版本，实施工程师可选择、检查、安装或升级。
- [ ] 停用加工必须先显示预览并二次确认；停用后不再产生新 L2 数据，但历史值、来源证据和稳定实体身份保留，再安装时复用原实体身份。
- [ ] 发布后 L2 身份稳定，实时值、历史和来源证据一致；修改加工规则不更换实体身份。
- [ ] 告警可以完成“选择 L2 实体 → 定义条件 → 发布 → 触发 → 恢复”。
- [ ] 节点管理主干用例只确认新 L2 实体能被告警配置选择；除非本轮专门验收告警，否则不发布告警规则、不触发动作。
- [ ] 调度策略只能绑定 L2，完成“新建 2充2放 → 绑定 SOC/功率实体 → 填时段和其他时段安全目标 → 试算 → 发布 → 启用 → 查看事件/控制回读 → 停用”。
- [ ] 试算不写设备；发布与启用是两个独立状态；启用策略只有在 committed L2 为 `GOOD` 且新鲜时才可形成控制意图。
- [ ] 调度策略只使用标准 GoRules JDM 作为内部执行语义；界面简表和完整规则图编辑的是同一份 JDM，不允许旧 `/rules`、简化表达式或第二套动作模型回流。
- [ ] 2充2放只列出 `bms.soc` / `storage.soc` 数值百分比输入及可写数值 `kW` 输出；直接调用 API 也不能绕过语义、类型、单位门禁，旧非法绑定不会被静默替换。运行与试算对 SOC 布尔值、非有限值和超出 0～100 的值均阻断，不形成控制意图。
- [ ] 修改名称、打开后关闭完整规则图、保存和刷新后，原 JDM、触发方式、时区、额外绑定和新鲜度契约保持一致；24:00 保留为当天结束，不变成 23:59。非内置 JDM 不得在保存时被默认 2充2放覆盖。
- [ ] 真实 PCS 闭环必须另行通过安全门：唯一写点、量程、联锁、权限、当前回读和输出所有权全部通过后，才允许小幅写入并用新 L2 回读确认。
- [ ] 旧待发/重试意图在领取及实际提交前重新检查当前策略、配置、有效 L1 来源、原始证据及当前 L2；新写栅栏覆盖停用/配置/来源并发，已发送命令仅回读；提交后关联前崩溃可按原幂等键恢复，不重复写。冷却竞争与安全栅栏不得互相等待。
- [ ] 若本轮涉及调度策略、控制或 EMS 工作台，必须分别完成其专项闭环；未涉及时不得顺带宣称完成。

默认在真实站点做只读浏览；若本轮改动涉及配置写入，则在隔离测试节点完成“检查 → 发布 → 结果查看”。调度策略自动验收使用无副作用试算；真实设备写入必须单独通过上述安全门。浏览器缺少有效登录会话时，保留页面并请用户登录，验收状态记为 `INCOMPLETE`。

普通节点管理改动以无头浏览器主干为默认验收；正式版本、Schema、数据帧、控制链等里程碑发布，再增加一次可见 Browser 抽查。无头测试失败时才用可见 Browser 复现和定位，避免每轮重复手工等待。

## 判定

- `PASSED`：全部自动检查通过，并且本轮涉及的人工业务检查已有证据。
- `FAILED`：任一已执行检查失败。
- `INCOMPLETE`：代码检查通过，但现场或人工证据尚未执行。
