# v0.4.82-rc.1 点位加工与 EN9 PCS 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将 v0.4.81 的 PCS 数据主干硬切换为“点位加工”，接入一号机恩玖 EN9 PCS 的 90 个只读 L0 输入，稳定产生 `pcs.active_power`、`pcs.operating_state`、`pcs.fault_codes` 三项 L2，并生成可部署、可验收、可整库回退的 `v0.4.82-rc.1`。

**Architecture:** 保留既有 `DataTrunk.ingest()` 原子运行主缝，把配置侧收口为 `PointProcessingDelivery.preview/apply/inspect`；Schema 040 在事务中完成旧 `point_conversion` 结构的硬改名和 BOOLEAN_SET 扩展。L0 与 L2 继续分别使用既有两张 hypertable，L1 只保存不可变配置；同节点 EN9 输入绑定 L0，不建设 rc.2 的跨节点 DSL。

**Tech Stack:** Python 3.13、FastAPI、Pydantic、PostgreSQL/TimescaleDB、React 18、TypeScript、Vite、Docker Buildx/GHCR、Docker Compose、Neuron REST API。

**Spec:** `docs/superpowers/specs/2026-08-23-point-processing-en9-cross-node-design.md`

## Global Constraints

- 本计划只交付 `v0.4.82-rc.1`；跨节点 DSL、DAG、时间窗口和历史重算分别留给 rc.2/rc.3。
- 术语与代码一次性使用 `点位加工`、`PointProcessing`、`point_processing`、`point-processing`；不得保留旧路由、别名、兼容视图、双写或 fallback。
- Schema 必须从完整 039 原子升级到 040；新应用遇到旧或混合 Schema 必须拒绝启动。
- EN9 首批严格为 90 个只读输入：1 个总有功功率、1 个并网/离网状态、88 个布尔故障点。
- L0 保存 Neuron 已换算的工程值；总有功功率不得重复执行 `decimal=0.1`。
- 任一必需故障输入 BAD/STALE 时，整个 `pcs.fault_codes` 为无值 BAD/STALE，不得输出不完整空集合。
- 不修改 Neuron、不发控制命令、不启用或验证自动策略；一号机仅做只读现场验收。
- 部署保持 `network_mode: host`、`tmpfs: /dev/mqueue`；不启动 Caddy、不申请 TLS。
- 不增加第三张 L1 时序表，不新增依赖，不把现场名称、连接参数或凭据写入解决方案资产和日志。
- 每个生产行为先执行 RED，再写最小实现并执行 GREEN；每个任务形成独立提交。
