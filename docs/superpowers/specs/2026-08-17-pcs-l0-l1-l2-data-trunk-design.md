# PCS L0—L2 数据主干第一纵向切片设计

**状态：** 已被 `2026-08-23-point-processing-en9-cross-node-design.md` 取代；仅保留为 v0.4.81 历史基线
**日期：** 2026-08-17  
**适用目标：** 以一台 PCS 和两种品牌模板证明“简单配置即可交付”的数据主干

## 1. 背景与问题

ZiZu 的目标数据主干由物理节点树以及挂载在节点上的三层数据视角构成：

- L0 原始点位保存协议网关采集的品牌事实；
- L1 点位转换保存版本化的品牌映射、换算、组合、质量和时间规则；
- L2 全局实体向告警、策略、控制、画面和报表提供稳定业务语义。

当前实现尚未形成这条可信主干：遥测历史和最新值分两次提交，buffer 会在数据库提交前清空；
公式转换仍是空实现；WebSocket 直接轮询 L0 最新值；实体实例虽已存在，但没有独立的 L2
历史、最新值、转换修订和来源证据。这使上层仍可能依赖品牌点位，也无法证明数据库失败、乱序、
转换升级和设备换牌时的工业语义。

本设计不一次建设所有设备与跨节点计算，而是先完成一个可交付、可替换品牌、可机器验收的 PCS
纵向切片，再将同一主干扩展到 BMS、光伏逆变器、充电桩和电表。

## 2. 目标与非目标

### 2.1 本轮目标

以一台 PCS 为首个纵向切片，同时证明三种常见转换：

1. 原始有功功率经过数值缩放和单位归一，形成 `pcs.activePower`（kW）；
2. 原始运行状态码经过枚举映射，形成 `pcs.operatingState`；
3. 原始字符串故障码经过多码拆分、规范化和故障映射，形成 `pcs.faultCodes`。

交付结果必须满足：

- 协议观测经同一个数据主干进入 L0 和 L2；
- L0、L2、最新值和 WebSocket outbox 在同一事务内形成一致事实；
- 数据质量、时间顺序、幂等、失败重试和来源证据具有明确语义；
- 实施工程师通过界面选择 PCS 品牌模板、处理少量歧义、预览计划并原子应用；
- 品牌 A 更换为品牌 B 后，L2 实体实例 ID 及上层引用保持不变；
- 公开协议模拟器、HTTP、WebSocket 和真实 PostgreSQL 生成机器验收证据。

### 2.2 本轮非目标

- 不完成所有 BMS、光伏、充电桩和电表模板；
- 不实现任意脚本或通用可编程表达式；
- 不实现跨节点多实体公式，首轮只为其保留“跨节点只能读取 L2”的约束；
- 不从 L2 读取公式反推 L0 控制地址；控制写入仍使用独立声明的安全动作；
- 不迁移全部旧 Tag/实体绑定；未迁移设备继续标记为兼容路径；
- 不在本轮完成连续聚合、高频波形或长期冷热分层；
- 不把一小时配置目标、一个工程日交付或四小时独立试验只凭开发测试宣称完成。

### 2.3 v0.4.81 发布边界

本纵向切片是 v0.4.81 的唯一开发主线。v0.4.81 不删除 v0.4.80 的兼容能力，不扩展 BMS、
光伏逆变器、充电桩或电表，也不把未迁移设备纳入 PCS contract gate。完成状态分为两个独立门禁：

1. **候选门禁：** Task 6—10 收口，公开协议、真实 PostgreSQL、REST、认证 WebSocket、重启、
   两品牌身份稳定、完整后端回归和前端构建全部通过，并生成固定 linux/arm64 镜像摘要；此时只能标记
   `v0.4.81-rc.1`，不得宣称现场可用。
2. **现场门禁：** 维护者明确确认维护窗口后，才允许备份、迁移并把固定摘要部署到 1号机；先完成
   只读数据主干验收，再执行受控低功率控制验收。现场证据全部通过后才能发布正式 `v0.4.81`。

候选门禁与现场门禁不得合并：开发完成不会自动触发部署，现场可访问也不能替代固定制品、迁移、
机器验收和回滚证据。

## 3. 已选方案

采用“应用层事务转换内核”。协议 adapter 负责解析输入，深模块 `DataTrunk` 负责固定转换修订、
计算 L2、持久化 L0/L2、推进最新值和生成 outbox。数据库 trigger 不承载业务转换；L2 也不通过
异步 eventual-consistency worker 在事务外补算。

选择该方案的理由：

- 相比数据库 trigger，转换规则可版本化、可独立测试，且不会把领域逻辑藏进 SQL；
- 相比异步双写，L0、L2 与推送事实可以在同一事务中生死与共；
- 相比继续扩展现有 pipeline，转换、质量、顺序和提交语义集中在一个深模块，协议、HTTP、
  调度器和测试只学习一个小接口。

## 4. 领域模型与不变量

### 4.1 物理节点树

节点树只表达站点、能源子系统和设备的物理归属，不把 L0、L1、L2 伪装为三层物理子节点。
用户选择 `PCS-01` 后，界面切换显示该节点的数据主干视图。

### 4.2 L0 原始点位

L0 是协议采集事实。每个点位具有稳定源键、数据类型、原始单位、源时间、接收时间、质量、
源消息 ID 或去重摘要及所属物理节点。L0 仅供工程诊断和本节点 L1 读取；上层业务不得直接消费。

### 4.3 L1 点位转换

L1 是不可变修订，不是实时值表。模板声明：

- 适用设备类别、品牌和型号；
- 强类型输入及匹配别名；
- 输出实体定义；
- 数值换算、枚举映射或多码解析规则；
- 输入质量合成、新鲜度和时间策略；
- 可选但独立声明的控制动作。

同一设备内的转换可读取本节点 L0。跨节点转换只能读取已经标准化的 L2，禁止直接跨节点引用
品牌 L0 点位。

### 4.4 L2 全局实体

L2 是站点内上层应用共同引用的稳定业务对象。“全局”表示跨应用统一可见，不表示跨站共享。
每个实体实例携带稳定身份、业务类型、单位、实时值、质量、业务时间、计算时间和来源证据。
告警、策略、控制、画面、历史和报表只能引用 L2 实体实例。

更换品牌或升级 L1 修订时，改变的是输入绑定与转换版本，不是 L2 实体实例 ID。上层引用不得
因品牌替换而修改。

## 5. 深模块与接口

外部 seam 只暴露一个高杠杆接口：

```python
class DataTrunk:
    def ingest(self, raw_observations: Sequence[RawObservation]) -> CommitReceipt: ...
```

调用者只需知道输入观测契约、幂等语义和返回的提交结果；不需要知道事务顺序、受影响转换查找、
质量传播、最新值条件更新、来源图或 outbox 结构。

`CommitReceipt` 至少返回：事务 ID、已接受或重复的 L0 数量、生成的 L2 事件 ID、未推进最新值的
迟到观测数量及持久失败引用。它只在数据库事务已经提交后产生。

模块内部包含三个明确职责：

1. **转换内核：** 读取已安装的固定 L1 修订，纯计算受影响的 L2 观测及来源证据；
2. **事务存储：** 在一个 PostgreSQL 事务中写入成功批次的全部 L0/L2/最新值/outbox；
3. **outbox 分发器：** 只读取已提交 outbox，向认证 WebSocket 发布，成功后标记发送状态。

事务存储 seam 具有 PostgreSQL adapter 和故障注入的内存 adapter，供同一接口验证原子性与回滚。
协议 adapter、现有 buffer 和 WebSocket 不复制转换或质量判断。

## 6. 提交数据流

每批协议观测依次执行：

1. parser/normalizer 产生强类型 `RawObservation`；
2. `DataTrunk` 用源消息 ID 或规范摘要去重；
3. 开启数据库事务并写入 L0 历史；
4. 仅当观测顺序更晚时推进 L0 最新值；
5. 按当前已安装且固定的 L1 revision 找到受影响输出；
6. 计算数值换算、状态枚举和多故障码集合，并生成质量与来源证据；
7. 写入 L2 历史；
8. 仅当业务时间及确定性 tie-breaker 更新时推进 L2 最新值；
9. 为实际推进的实时变化写入同事务 outbox；
10. 提交事务并返回 `CommitReceipt`；
11. pipeline 收到 receipt 后才从 buffer 移除已确认观测；
12. outbox 分发器在提交后推送，客户端按 L2 `event_id` 去重。

任一数据库步骤失败时，L0、L2、最新值和 outbox 全部回滚，不允许出现“L0 已写、L2 未写”或
“数据库未提交、界面已刷新”。

## 7. 质量、时间与失败语义

### 7.1 质量枚举

质量固定为：

- `GOOD`：值有效，可供画面、告警、策略和控制依据使用；
- `UNCERTAIN`：可保留计算值，界面以琥珀色显示；不得作为自动策略或控制依据；
- `BAD`：没有有效当前业务值，强类型值为空；
- `STALE`：在声明的新鲜度窗口内没有新观测，强类型值为空。

BAD 和 STALE 必须进入 L2 历史与最新值，并携带原因、源时间、计算时间和来源证据。界面可以另行
显示 last GOOD，但不得把它伪装为当前值。

### 7.2 PCS 三类规则

- 数值超出模板声明范围：`BAD / OUT_OF_RANGE`；
- 未识别运行状态码：`BAD / UNMAPPED_ENUM`；
- 故障字符串中含未知代码：保留未知原码，整体为 `UNCERTAIN / UNMAPPED_FAULT_CODE`；
- 必需输入缺失、类型或单位不匹配：L0 事实仍可保存，但输出 L2 写入明确失败质量，禁止猜测；
- 多码结果先拆分、去空、规范大小写、去重并稳定排序，再映射为强类型 `CODE_SET`。

### 7.3 乱序与新鲜度

迟到观测可以进入 L0/L2 历史，但不能倒退任何最新值，也不能产生实时 WebSocket 更新。相同业务
时间使用稳定 source sequence 或观测摘要作为 tie-breaker，保证重放结果一致。

新鲜度调度器属于 `DataTrunk` 的 implementation，并复用其内部事务执行器产生 STALE 观测，而不是
伪造 L0 原始点位或直接修改 L2 最新值；因此历史、最新值、outbox 和上层状态仍保持原子一致，
也不为调用者增加第二套写入 interface。

### 7.4 重试与持久失败

pipeline 只在 receipt 后确认并移除 buffer 项。瞬态失败使用有界退避重试；超过阈值后，以独立的
失败记录事务写入 `t_ingestion_failures` 并产生运行告警，保留可重放的源消息引用、失败阶段和安全
摘要。该失败事务不能携带任何部分 L0/L2 业务写入。凭据、完整协议地址和敏感原始内容不得进入
日志、审计或 WebSocket。

## 8. 关系与时序结构

### 8.1 配置关系表

目标关系结构包括：

- `point_conversion_templates`：设备类别、品牌、型号和模板身份；
- `point_conversion_revisions`：不可变模板内容摘要、版本和发布时间；
- `point_conversion_inputs` / `point_conversion_outputs`：强类型输入输出契约；
- `numeric_transform_rules`：数值缩放、偏移、范围和单位；
- `enum_mapping_entries`：原始状态到标准枚举的唯一映射；
- `fault_code_mapping_entries`：原码、标准码、名称和默认严重度语义；
- `point_conversion_plans` / `point_conversion_plan_items`：基准站点版本、摘要、变更和阻断；
- `installed_point_conversions`：节点当前安装的模板 revision 与站点配置版本；
- `conversion_input_bindings`：输入契约到 L0 点位或允许的 L2 输入的确认绑定；
- `conversion_output_bindings`：输出契约到既有 L2 实体实例的稳定绑定。

核心关系使用外键、唯一约束、枚举和 CHECK 约束；JSON 只承载非关键展示元数据，不替代输入、输出、
单位、类型、绑定、修订和来源关系。

### 8.2 L0 与 L2 时序

现有 `t_telemetry` 和最新值表正式收敛为共享 L0 历史与 L0 latest，并补齐稳定观测 ID、源消息 ID
或摘要及顺序字段。本轮新增：

- `t_l2_observations`：共享 L2 hypertable；
- `t_l2_latest`：每个实体实例的当前观测；
- `t_l2_observation_sources`：L2 观测到一条或多条输入观测的来源关系；
- `t_l2_stream_outbox`：提交后 WebSocket 事件；
- `t_ingestion_failures`：超过重试阈值的持久失败。

L2 观测使用互斥强类型列：

```text
value_float | value_int | value_bool | value_text | value_codes[]
```

有效值只能命中与实体类型相符的一列；空 `value_codes[]` 是“当前无故障码”的有效 GOOD 值，
而 BAD/STALE 时所有值列必须为空。每条 L2 历史至少保存实体
实例、业务时间、接收时间、计算时间、质量、原因、转换 revision、站点配置版本、来源摘要和事件 ID。

L1 默认不保存每个中间值。L0、L2、转换 revision 和来源关系必须足以解释结果。连续聚合与长期存储
在后续历史优化票据中建设，不阻断本轮 raw L2 history 的公开查询。

## 9. 配置计划与原子安装

实施工程师在物理节点树选择 PCS 节点和品牌型号后，平台按模板的稳定源键、别名、数据类型和单位
自动匹配 L0。计划项固定为：

- `add`：新增转换或输出绑定；
- `update`：替换 revision 或输入绑定；
- `preserve`：当前绑定与内容完全一致；
- `delete_candidate`：旧转换不再需要，但历史和来源证据保留；
- `block`：缺失、歧义、类型、单位或并发冲突。

所有必需输入必须 100% 可解析。零候选或多候选都形成结构化 blocker，禁止按名称相似度、创建
顺序或所谓优先级静默选择。已支持模板所需 L0 的总体自动匹配率目标不低于 95%，剩余少量歧义由
实施工程师按可读点位名处理，界面不暴露 UUID、SQL 或 JSON/YAML。

应用计划必须在同一事务中：锁定站点配置、复核 plan digest 与基准版本、安装 immutable revision、
写入输入/输出绑定、保持 L2 实体身份、推进站点配置版本并追加审计。任何 blocker 或复核失败都
保持零运行写入。相同 actor 和幂等键重放返回同一结果；不同请求复用键稳定拒绝。

## 10. 公开接口与权限

首轮公开接口：

| 方法 | 路径 | 能力 |
|---|---|---|
| GET | `/api/v1/point-conversion-templates?device_category=PCS` | 查询适用模板 |
| GET | `/api/v1/nodes/{node_id}/data-trunk` | 查看节点 L0/L1/L2 完整性与当前绑定 |
| POST | `/api/v1/nodes/{node_id}/point-conversion-plans` | 生成确定性计划 |
| GET | `/api/v1/point-conversion-plans/{plan_id}` | 回读计划、摘要和 blocker |
| POST | `/api/v1/point-conversion-plans/{plan_id}/apply` | 幂等原子应用 |
| GET | `/api/v1/entity-instances/{id}/realtime` | 读取 L2 当前业务观测 |
| GET | `/api/v1/entity-instances/{id}/history` | 读取 L2 历史及版本标记 |
| WS | `/api/v1/ws/entity-observations` | 订阅提交后的 L2 增量 |

权限固定为：

- admin：导入、发布和停用点位转换模板；
- engineer：选择模板、匹配输入、生成和应用计划、运行机器验收；
- operator：只读 L2 实时、历史和来源摘要；
- 所有拒绝和配置操作进入既有统一审计；只有 `/health/live` 保持匿名。

HTTP 与 WebSocket 使用同一身份与能力语义。WebSocket 订阅期间持续重验 session；令牌不得放在
query string。

## 11. 引导式交付驾驶舱

首轮不另建自由设计器，而是在既定交付驾驶舱中实现 PCS 纵向切片：

1. 顶部固定五阶段：节点树、连接与模板、匹配与预览、处理阻断、安装与验收；
2. 左侧物理节点树显示 PCS 节点及数据主干完整性；
3. 中部按 `L0 → L1 → L2` 展示原始点位、转换规则和输出实体；
4. 右侧只显示匹配率、必需输入完整度、blocker、下一动作和验收进度；
5. 计划预览显示 add/update/preserve/delete_candidate/block 的数量和逐项可读差异；
6. blocker 未清零时禁用安装；应用后自动进入机器验收；
7. L2 实时卡显示值、单位、质量、数据年龄、转换版本和来源摘要；
8. 工程师可从 L2 下钻 L1/L0，operator 默认只看 L2；
9. 品牌替换视图明确显示“输入绑定变化、L2 身份不变、上层消费者不变”。

EMS 运行工作台继续独立存在，首页优先显示能流、SOC、功率、设备可用性、告警和质量，不退化为
工程点位表。

## 12. 稳定错误与安全失败

至少固定以下错误语义：

- `POINT_CONVERSION_INPUT_MISSING`：必需输入无候选；
- `POINT_CONVERSION_INPUT_AMBIGUOUS`：必需输入有多个候选；
- `POINT_CONVERSION_TYPE_MISMATCH`：输入数据类型不兼容；
- `POINT_CONVERSION_UNIT_MISMATCH`：输入单位不兼容；
- `POINT_CONVERSION_PLAN_STALE`：站点配置或候选目录已变化；
- `POINT_CONVERSION_PLAN_DIGEST_MISMATCH`：计划内容与保存摘要不一致；
- `POINT_CONVERSION_NOT_INSTALLED`：节点没有可执行的已安装 revision；
- `DATA_TRUNK_UNAVAILABLE`：身份之后的数据主干存储或转换目录不可用；
- `IDEMPOTENCY_KEY_REUSED`：同一幂等键用于不同请求。

错误沿现有 `{"detail":{"code","message"}}` 包络。所有故障 fail closed：不得回退到旧 Tag、
不得绕过 L2 直接向上层供值、不得在审计或 outbox 中泄漏凭据和完整协议地址。

## 13. 机器验收

首轮完成定义不是“页面可打开”，而是公共主缝产生不可变验收证据。验收使用公开协议模拟器，
真实经过 parser、normalizer、`DataTrunk`、PostgreSQL、REST、认证 WebSocket 和上层消费接口，证明：

1. L0 历史与 latest 均保存真实协议观测；
2. 数值换算、枚举映射、多故障码解析结果和单位正确；
3. L2 历史/latest 保存转换 revision、站点配置版本和完整来源证据；
4. GOOD、UNCERTAIN、BAD、STALE 的值与上层使用限制正确；
5. 迟到观测进入历史但不倒退 latest、不产生实时推送；
6. 重复消息幂等，任意事务步骤失败均无部分写和虚假推送；
7. outbox 仅在提交后发布，重复投递可由 event ID 去重；
8. 进程重启后配置、L0/L2 历史、latest 和验收证据保持一致；
9. 从品牌 A 切换到品牌 B 后 L2 实体 ID、告警/策略/画面引用保持不变；
10. admin/engineer/operator 的允许和拒绝行为、拒绝审计及零越权写入成立。

机器报告至少锁定平台版本、Schema 版本、模板 revision、站点配置版本、L2 实体 ID、逐项证据摘要
和执行时间。开发测试不能替代后续一小时、工程日和四小时独立交付试验。

## 14. 迁移与兼容边界

### 14.1 Expand

- 复用并补强现有 telemetry 表为 L0；
- 新增 L1 关系、L2 时序、outbox、失败队列和计划表；
- 实体实例来源显式区分 `legacy_tag` 与 `point_conversion`；
- 先让新表和新路径与旧路径并存，不改写历史事实。

### 14.2 Migrate

- 提供不含客户参数的 `reference-pcs-brand-a` 与 `reference-pcs-brand-b`；
- 两种模板使用不同原始点位名、状态码和缩放，但输出同一组三个 L2 语义；
- 新 PCS 只走 `DataTrunk`；完成迁移的 PCS 告警、策略和 EMS 页面只引用 L2；
- 未迁移设备明确显示兼容状态，不把部分迁移宣称为全站完成。

### 14.3 Contract

只有 PCS 主缝通过完整机器验收后，才对该范围执行 contract gate：

- 阻止新建 `legacy_tag` 直接实体绑定；
- 删除 migrated PCS 的 L0 直接业务读取和运行期 legacy fallback；
- 用路由覆盖、静态扫描和数据库约束证明上层不能绕过 L2；
- 旧历史保持只读可追溯；旧 latest 和写路径待所有消费者迁移后再删除。

`point_conversion` 缺失、损坏或不可用时必须显式失败，绝不能回退旧数据源掩盖故障。

## 15. 实施顺序约束

后续实施计划必须保持纵向 TDD，每个切片从公共 seam 先得到 RED，再写最少实现。顺序应先证明
单条 PCS 数值转换与事务原子性，再加入枚举、多码、质量/时间、outbox、计划安装、品牌替换和驾驶舱；
不能先铺开所有设备模板、通用表达式或全站 UI。

任何阶段都不得提前声称“全站数据主干已迁移”或“简单配置目标已完成”。首轮完成的准确表述是：
“PCS 的 L0—L2 数据主干纵向切片已通过机器验收，并证明两品牌替换不改变上层业务身份。”
