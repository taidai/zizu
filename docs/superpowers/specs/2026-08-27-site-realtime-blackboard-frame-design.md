# 单站实时黑板与数据帧设计

**状态：** 架构已确认，书面规格待最终复核
**日期：** 2026-08-27
**适用主线：** 节点 → L0 原始点位 → L1 点位加工 → L2 全局实体 → 告警 / JDM / 控制 / 画面

## 1. 目的

光伏、储能、充电桩和电网设备会在不同时间送来数据。平台需要先把这些零散数据放进一块单站
“实时黑板”，再按统一节拍取得一张可重复解释的数据照片，完成 L1 点位加工，最后把已经提交的
L2 结果交给页面和上层应用。这样既不要求每个点位同时到达，也不会让页面、告警和控制看到一半新、
一半旧的处理中状态。

本设计增加的是数据主干的运行机制，不增加新的产品层级。节点、L0、L1、L2 仍是平台唯一主干。

## 2. 一句话方案

每个单站只有一块常驻内存的全量实时黑板和一个默认 1 秒的拍照节拍；收到更新就覆盖对应格子并
标脏，到点时只有黑板发生变化才冻结一个完整数据帧，先批量保存本帧的新 L0，再用完整帧运行一次
全部已安装 L1，批量保存 L2、来源证据和 outbox，数据库提交成功后才通知实时页面、告警、JDM、
控制和画面。

## 3. 范围与不做项

### 3.1 本轮必须解决

- 异步点位如何形成同一计算批次；
- 重复、迟到、缺失和陈旧数据如何处理；
- 如何减少无变化时的数据库读写和 CPU 占用；
- L0 与 L2 如何共享统一帧身份、配置修订和来源证据；
- 进程重启或 L1 失败后如何恢复且不丢已提交 L0；
- L0 点位实时数据和 L2 实体实时数据如何一致地显示。

### 3.2 明确不做

- 不引入 Redis、Kafka、新微服务或通用流处理平台；
- 不为点位、节点或 L0/L1/L2 分别建立超级表；
- 不保存整块黑板的大 JSON；
- 不支持每点、每节点各自节拍，首版每站只有一个节拍；
- 不把窗口累计、日月统计塞进帧内 L1；它们继续作为既有 L2 统计实体运行投影；
- 不补写迟到样本，不承诺波形级、毫秒级或零丢失采集；
- 不新增“黑板管理”产品页面或自由脚本配置器。

## 4. 架构总图

```text
Neuron / NanoMQ / 协议适配
             │ 异步原始样本
             ▼
┌────────────────────────────────────────────┐
│ 单站实时黑板（内存，进程内唯一）           │
│ 每格：值、源质量、有效质量、数据时间、      │
│       接收时间、源顺序、脏标记、漏拍计数    │
└────────────────────────────────────────────┘
             │ 每站统一节拍；无变化不拍
             ▼
      冻结完整不可变数据帧
             │
             ├─ 事务 A：帧元数据 + 本节拍新 L0 → PENDING
             │                                      │
             │                                      ▼
             │                         可恢复的帧处理器
             │                                      │ 全量 L1 一次
             │                                      ▼
             └─ 事务 B：L0 latest + L2 历史/latest
                        + 来源证据 + outbox + COMPLETE
                                               │ 提交后
                                               ▼
                           实时页面 / 告警 / JDM / 控制 / 画面
```

“同一时刻”在这里表示一次原子冻结形成的**一致计算切面**，不表示所有现场仪表真的在同一微秒完成
采样。每格仍保留自己的数据时间和质量，平台不会伪造现场同步性。

## 5. 实时黑板

### 5.1 唯一职责

实时黑板只负责接收每个活动 L0 点位的最新候选值、判断新旧、维护新鲜度并冻结数据帧。它不是历史
数据库，也不是上层应用的数据源；数据库中的已提交结果才是可恢复事实。

单站同一时刻只允许一个活动采集写者持有黑板。首版部署不支持 active-active backend；启动时使用
站级数据库锁确认唯一写者，拿不到锁就保持 NOT_READY，绝不能让两块黑板同时为同一站拍照。

每个格子至少包含：

- L0 点位稳定身份；
- 当前值；
- 原始质量与按新鲜度计算后的有效质量；
- 设备数据时间、平台接收时间；
- 规范化源顺序；
- 本节拍是否收到新样本；
- 连续未收到新样本的节拍数。

### 5.2 新样本与迟到样本

协议适配层为每条样本生成可比较的 `source_order`：优先使用可信源序号，其次使用可信设备时间并加
确定性次序，均不可信时使用平台接收次序。只有 `source_order` 严格大于格子当前值才算新样本；相等
或更小的重复、乱序和迟到样本直接丢弃，不进入黑板、L0 历史、L1 或实时推送。进程重启时从已保存
L0 恢复每格最后源顺序，不能因内存清空而重新接纳旧样本。

同一节拍内同一点位可能连续到达多次，黑板只保留最后一条已接受样本。拍照时每个变化点位最多保存
一条 L0，明确以秒级 EMS 状态采样换取有界写入，不把平台做成波形记录仪。

### 5.3 启动与配置变更门槛

运行配置发布时，根据已安装 L1 的确定性依赖图计算“必需 L0 集合”；跨节点 L2 输入继续沿依赖图
追溯到实际必需的 L0。可选输入和与 L1 无关的诊断点位不阻塞启动。

进程启动、重启或必需集合变化后，每个必需 L0 都必须实际收到至少一条本轮新鲜样本，黑板才进入
READY 并产生第一帧。收到 BAD 样本也表示该点位已经到达，但其质量会继续向 L2 传播；它不能让控制
通过质量门禁。旧数据库 latest 可供只读诊断，不得冒充本轮新鲜输入启动计算或控制；WARMING 期间
实时读取必须按当前时间把过期旧结果显示为 STALE，不能继续显示成可用的 GOOD。

### 5.4 新鲜度

每次站级节拍都推进新鲜度：本节拍收到新样本则漏拍计数归零；没有收到则加一。连续漏过 3 个节拍
时，格子保留最后值供诊断，但有效质量改为 `STALE`。质量变化本身会把黑板标脏，因此即使没有新值，
也会拍一帧并把陈旧状态送到 L2。之后收到新样本时，漏拍归零，有效质量恢复为该样本实际质量，而
不是一律伪装成 GOOD。L0/L2 的 STALE latest 保留最后已知值并醒目标记质量，方便现场排障；告警、
JDM 和控制必须按质量拒绝它，不能只因数值非空就使用。

站级计时器每拍递增 `capture_beat`，即使本拍不生成数据帧也递增。每条新 L0 记住它实际到达的
`accepted_beat`；数据帧保存冻结时的 `capture_beat`。因此任意格子的漏拍数都能稳定重建为
`capture_beat - accepted_beat`，不需要持久化整张黑板或每拍写数据库。进程启动时从数据库已保存的
最大拍号继续递增，不得从零重新编号。

### 5.5 配置修订栅栏

配置发布与拍照共用同一站级栅栏。发布先暂停生成旧修订新帧，继续接收但只保留每点最新候选，再用
有界等待排空当前帧队列和未发布 outbox；超时就零配置写入、恢复旧修订拍照。排空成功后才原子激活
新配置修订并使黑板进入新一轮 WARMING；栅栏期间保留的候选从切换成功时起归入新修订。

WARMING 期间，上一修订的 committed L2 只可作为 STALE 诊断值。页面、告警、JDM 和控制必须同时
检查 `configuration_revision == active_revision`；在新修订必需 L0 全部新鲜到达并提交首帧之前，旧
修订结果不得继续驱动业务。自动控制命令在真正写设备前还要重验其来源帧修订；已经排队但属于旧
修订的命令必须拒绝，不能只以“生成命令时合法”为由继续执行。这样不会出现新配置已经生效、旧
PENDING 帧或旧控制意图却晚到并恢复业务驱动的情况。

## 6. 拍照规则

- 每站只有一个 `snapshot_interval_ms`，首版固定默认值 1000ms；不提供产品级调参页面；
- 节拍持续运行并递增 `capture_beat`，以便计算漏拍和 STALE；
- 黑板未 READY 时不产生业务帧，只报告 WARMING 运行状态；
- READY 后若没有新样本或质量变化，跳过本次拍照，不写数据库；
- 有变化时，在极短临界区内冻结一份不可变全量视图；事务 A 再从数据库分配站内帧序号，数据库操作
  不占用黑板锁；
- 冻结期间或之后到达的数据写入下一代黑板，只能进入下一帧；
- 帧内包含全部活动格子的当前状态，L1 使用其中的确定输入；L0 历史只写本节拍真正变化的最新样本，
  不给旧值换时间戳，也不为纯 STALE 转换伪造设备样本；
- 进程在拍照前崩溃时，最多损失一个节拍内尚未落库的候选样本；系统保留上一个已提交结果并按时间
  变陈旧，不补造数据。

## 7. 两段持久化与 L1 执行

### 7.1 事务 A：先保住 L0

一次批量事务完成：

1. 写入数据帧元数据，状态为 `PENDING`；
2. 批量写入本帧真正变化的 L0 历史，并记录 `frame_id` 与样本的 `accepted_beat`；
3. 提交。

事务 A 不公开推进 L0 latest，也不发送 WebSocket。这样 L1 即使失败，原始事实仍然存在；同时用户
不会看到尚未得到对应 L2 的半成品画面。

### 7.2 帧处理器

单站帧处理器按帧序号领取最早的 `PENDING` 帧，使用短租约避免进程崩溃后永久占用。正常路径直接
使用冻结的内存视图；重启恢复时，从 L0 历史按不大于本帧序号的最后观测重建同一全量视图，并加载
帧所固定的不可变 L1 / 配置修订；有效质量由帧的 `capture_beat` 与每条来源的 `accepted_beat` 精确
重算，不能用重启时刻重新猜测。

首版每个数据帧对全部已安装的即时型 L1 规则运行一次，按既有跨节点强类型 DAG 拓扑求值。先不做
“只计算受影响规则”优化；只有现场性能证据证明全量计算不足时才增加该复杂度。

### 7.3 事务 B：提交可见结果

一次批量事务完成：

1. 将本帧完整视图所引用、且比公开 latest 更新的 L0 推进到 `t_telemetry_latest`；
2. 为所有活动 L2 输出写入本帧历史和 latest；
3. 写入 L2 到实际 L0 观测的来源关系，未变化旧输入可引用以前帧的 L0 观测；
4. 写入一条只引用终态帧身份的 outbox，不在数据库嵌入整帧 JSON；
5. 将帧标记为 `COMPLETE`；
6. 提交后再由既有 outbox 通知实时页面、告警、JDM、控制和画面。

对新主干，L0/L2 latest 的首要比较键统一为 `frame_sequence`；样本业务时间继续保存用于显示、追溯
和统计，但不再决定终态可见顺序。这样保留旧数据时间的 STALE 帧仍能覆盖先前 GOOD，重试或旧帧又
不能倒退 latest。现有 L2 `commit_sequence` 直接使用同一帧序号，不再维护第二套顺序。

上层消费者只处理终态已提交帧，并以 `frame_id + observation/event_id` 幂等。控制继续执行既有 GOOD
质量、授权、限值和回读门禁，不能因为黑板里“有一个旧值”就放行。

## 8. 数据结构

### 8.1 数据帧表

新增一张共享 `t_data_frames`，不按站点、节点或层级拆表。最小字段为：

```text
frame_id
site_id
frame_sequence        -- 站内单调递增；现有 L2 commit_sequence 与它保持同一顺序
capture_beat          -- 每拍递增；包含未生成数据帧的空拍
shot_at
configuration_revision
status                -- PENDING | PROCESSING | COMPLETE | FAILED
attempt_count
lease_until
failure_code
created_at
finished_at
```

`(site_id, frame_sequence)` 唯一。帧固定配置修订，使恢复时不会拿新公式重算旧帧。

### 8.2 共享时序表

- `t_telemetry`：继续作为唯一 L0 时序表，增加 `frame_id`；新主干写入必须非空，旧历史保留 NULL，
  不为迁移前数据伪造帧；新行同时保存 `accepted_beat`，每帧只含变化点位的最新样本；
- `t_telemetry_latest`：只代表最新终态可见帧，不代表尚在处理的 PENDING 帧；
- `t_l2_observations`：继续作为唯一 L2 时序表，增加 `frame_id`；新主干写入必须非空，旧历史保留
  NULL；每个 COMPLETE 帧保存所有活动 L2，FAILED 终结只保存受影响 L2 的 STALE 结果；
- `t_l2_latest`：每个 L2 实体实例的最新终态结果；
- `t_l2_observation_sources`：继续保存 L2 到 L0 的来源证据；
- `t_data_frame_outbox`：由现有 `t_l2_stream_outbox` 一次硬切改名，每个 COMPLETE 或 FAILED 终态帧
  一条，只保存帧身份、发布状态和重试信息；分发时按帧读取 L0/L2 并生成一个原子事件包。

不建立 L1 时序表。L1 是版本化加工配置；运行证据由数据帧、L0、L2、加工修订和来源关系共同组成。
现有防重复缓存继续只承担短期防重，不重新变成永久证据。

## 9. 失败、重试与恢复

- 单站使用一个有界帧队列，不增加消息中间件；
- `PROCESSING` 租约超时后可由同一处理器重新领取；
- 首版采用固定、不可在页面配置的失败预算：最多 3 次处理尝试，帧总年龄不超过 60 秒；
- 超过任一预算后，将帧终结为 `FAILED`，持久记录原因，产生系统告警，并把受影响 L2 以
  `FRAME_PROCESSING_FAILED` 原因转为 STALE；
- “受影响 L2”必须取失败输出在当前强类型 DAG 中的全部传递下游闭包；无法可靠定位失败源时，宁可
  把本帧全部活动 L2 标为 STALE，也不能留下仍可被控制使用的旧 GOOD 下游；
- FAILED 终结事务同时推进本帧已提交的 L0 latest、写入受影响 L2 的 STALE 结果和 outbox，提交后才
  公开；因此失败也不会让页面看到只有 L0、没有质量结论的半帧；
- 失败帧保留已经提交的 L0，绝不回滚或删除；终结后继续处理后续帧，不形成无限积压；
- latest 的推进必须比较帧序号，任何重试或较老帧都不能把可见状态倒退；
- 数据库不可用时不伪装成功、不提前推送；恢复后从 PENDING 或租约过期的 PROCESSING 继续。

## 10. 实时页面与数据流

节点详情的“点位”显示 L0，节点详情的“全局实体”和 EMS 工作台显示 L2。两类页面都遵循同一规则：

1. 首次打开或断线重连时，用一次 REST 读取完整的最新终态快照；响应同时返回帧序号游标；
2. WebSocket 从该游标以后只推送已经提交的数据帧增量；
3. 若 outbox 已无法覆盖旧游标，服务端明确要求客户端重新读取完整快照；
4. 页面按帧原子应用增量，显示值、质量、数据时间、接收时间和帧时间；
5. L0 和 L2 的更新都在事务 B 提交后才可见，不再每 1.5 秒轮询数据库；
6. 告警、JDM、控制和画面与页面消费相同的 committed L2 seam，不另开旁路。

因此正常链路是“设备 → 黑板 → 数据帧 → 数据库提交 → WebSocket”，不是 WebSocket 先跑、数据库
后补。数据库是真相，WebSocket 是送达方式。

## 11. 模块边界

首版只保留三个深模块，不铺设一层层转发服务：

- `RealtimeBlackboard`：接收新样本、拒绝旧样本、推进新鲜度、按需冻结；
- `FrameRepository`：原子保存 PENDING L0 帧、领取/恢复帧、原子完成 L2 或终结失败；
- `FrameProcessor`：加载固定修订、对完整帧运行既有 L1 DAG、生成 L2 与来源证据。

既有 `DataTrunk` 对外仍是数据主干入口，但内部改为调用这三个职责；上层只能订阅提交后的 outbox。
不为当前只有一个实现的细节提前增加插件接口。

## 12. 与现状的差距及迁移边界

这是目标设计，不代表 v0.4.85-rc.4 已经实现。当前实现仍存在“单次 ingest 中 L0/L2 同事务”、
L0 WebSocket 定时读取 latest、无数据帧元数据和无单站黑板节拍等差距。

本设计取代旧数据主干规格中“迟到观测仍进 L0 历史”的规则，并把 STALE 调整为“保留最后已知值、
质量不可用”；BAD 仍可按既有规则保存空值。机器消费者必须检查质量，不能继续把空值当作唯一安全
门槛。它也取代旧点位加工规格中即时 L2 按实体周期写历史或写心跳的规则：即时 L2 只随站级变化帧
提交，窗口统计仍走独立的 L2 运行投影。旧 EN9 规格中每输入至少 5 秒的新鲜度下限和按业务时间推进
latest 的规则也由本设计取代；活动必需输入的采集周期必须在配置发布时校验为不超过 3 个站级节拍，
否则阻止发布，而不是运行时偷偷采用另一套阈值。参考光储充 EMS 要求必需源按站级节拍或更快周期
发送，即使数值不变也要有周期样本；纯变化上送且没有心跳的源不能作为必需控制输入。

后续实现采用一次明确 Schema 演进并保持现有共享表，不重建整套数据模型：

1. 先加 `t_data_frames`、帧外键和终态读取约束；
2. 用 TDD 建立黑板、拍照、迟到丢弃、三拍 STALE 与启动门槛；
3. 将写入拆成事务 A / 事务 B，并证明 L1 失败不丢 L0；
4. 建立恢复、有限重试、失败告警和序号防倒退；
5. 将 L2 outbox 硬切为单一数据帧 outbox，并把 L0 实时显示迁到“完整快照 + committed 增量”，删除
   1.5 秒数据库轮询；
6. 最后执行 contract gate，禁止告警、JDM、控制和画面绕过 committed L2。

迁移期间不得双重通知上层，不得让同一站同时存在两套帧顺序语义。正式计划需另行编写和确认。

## 13. 验收标准

实现只有同时证明以下行为才算完成：

1. 必需 L0 未全部新鲜到达时状态为 WARMING，不运行 L1 或控制；全部到达后只产生一张首帧；
2. 无变化持续 60 秒时，不新增帧、L0/L2 历史或 outbox 写入；
3. 同点位一拍内多次更新只保存最后一条，重复和迟到数据完全不入库、不推送；
4. 连续三拍无新样本时产生一次 STALE 转换帧，新样本恢复实际质量；
5. 每张成功变化帧只提交一份全量即时 L1 结果；失败重试不得产生重复结果，L0/L2 具有相同
   frame/configuration revision 和可追溯来源；
6. 事务 A 成功而 L1 或事务 B 失败时，L0 仍存在，页面和上层看不到半成品；
7. 进程在 PENDING、PROCESSING 和 outbox 各阶段重启后均可恢复，且 latest 不倒退、通知可幂等；
8. 失败帧在固定预算内终结、告警、使相关 L2 STALE，并继续后续帧；
9. 页面首次读取完整终态快照，随后只收 committed 增量；断线游标过旧时明确重读；
10. 代表性光储充站点负载下，数据库写入以每帧两次批量事务为主，不随点位数退化为逐点 SQL，
    backend 无忙循环且实时延迟不超过既有 30 秒现场门禁；
11. 所有自动控制只读取 committed、质量合格的 L2，并继续通过统一控制命令及回读确认。
12. 纯 STALE 帧在事务 A 后重启，能凭 capture/accepted beat 重建出与崩溃前完全相同的质量结果；
13. 配置发布在旧帧或 outbox 未清空时零写拒绝；切换后旧修订结果保持 STALE，直到新修订首帧完成；
14. 任一 L1 输出失败时，其全部跨节点下游闭包同帧转为 STALE；无法定位时全部活动 L2 fail closed。

## 14. 已确认结论

本方案选择“单站内存黑板 + 有变化才拍完整帧 + L0 先持久化 + L1 全量计算 + L2 提交后通知”，
接受迟到数据丢弃、同节拍中间样本不留历史和进程崩溃时最多损失一拍未落库候选的代价，换取一条
简单、可解释、可恢复且数据库负担有界的秒级光储充 EMS 数据主干。
