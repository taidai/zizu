# L0→L1→L2 用户体验设计

## 1. 目的

让实施工程师不必先学习 L0、L1、L2 术语，也能完成一台设备从接入到交付的全过程：选择设备，查看
原始数据，套用或调整点位加工模板，检查生成的实体，确认后发布；以后实时、历史、告警、画面、JDM
和控制都使用这些实体。

内部架构仍严格遵守：

```text
真实节点树 → L0 原始点位 → L1 点位加工 → L2 全局实体 → 上层应用
```

产品界面不把三层包装成三套管理系统，而是在所选真实节点下提供三个任务页面：

```text
原始点位｜点位加工｜实体数据
```

## 2. 用户能看懂的对象

| 页面名称 | 用户要解决的问题 | 内部含义 |
| --- | --- | --- |
| 原始点位 | 设备现在送来了什么，过去送过什么 | L0 |
| 点位加工 | 怎样把品牌点位变成平台统一含义 | L1 |
| 实体数据 | 上层功能现在可以使用什么，过去是什么 | L2 |

界面以中文任务名称为主；L0/L1/L2 只作为辅助标识、帮助说明或技术详情，不要求用户记忆。

“实时”和“历史”是同一个点位或实体的两种查看方式，不创建“实时点位”“历史点位”“实时实体”或
“历史实体”等重复对象。

## 3. 原始点位

### 3.1 实时

默认以可搜索列表显示点位名称、当前值、单位、质量、最后数据时间和来源。GOOD、UNCERTAIN、BAD、
STALE 使用统一中文状态；STALE 保留最后值，但明确显示数据已经过期。

### 3.2 历史

用户从同一条点位进入历史，选择时间范围后查看趋势或明细。默认保存 7 天 L0 明细；更长时间不是
普通交付需求。历史只显示已经提交的原始事实，不把 L1 或 L2 结果混进 L0。

## 4. 点位加工

### 4.1 默认交付路径

```text
选择设备
  → 系统按设备类型、品牌和系列推荐模板
  → 确定匹配的点位自动绑定
  → 用户处理缺失或歧义输入
  → 在线试算
  → 检查 L2 输出预览
  → 检查并发布
```

系统只能自动绑定完全确定的点位；零候选或多候选都必须留给用户确认。缺少必需输入、类型/单位错误、
循环依赖或试算失败都会阻止发布，并给出“哪个输入、为什么、怎么处理”的中文说明。

### 4.2 加工编辑器

编辑器只在点位加工页面使用三栏：

```text
L0 输入            加工规则               L2 输出预览
设备原始点位   →   映射/换算/公式/统计  →  名称、值、单位、质量
跨节点 L2      →   强类型校验           →  来源与结果
```

首版只提供五类强类型加工：直接映射、单位换算、状态映射、公式计算、统计加工。公式只能引用系统提供
的点位或实体，发布前检查类型、单位和依赖关系，不允许任意脚本。跨节点计算只能读取已发布 L2，不能
读取其他节点 L0。

统计加工由“来源实体、计算方法、时间窗口、时区”组成，例如 15 分钟平均功率或日充电量；它只是 L1
的一种加工方式，输出仍是普通 L2 实体，不新增 L3 或独立统计实体系统。

### 4.3 模板复用与升级

点位加工模板按设备类型、品牌和系列复用。实例上的绑定调整默认只影响当前设备；确有复用价值时，
管理员才显式保存为新模板修订。已投运设备不自动升级模板；页面先展示差异和试算结果，再由用户确认
升级，失败时继续运行旧修订。

## 5. 实体数据

### 5.1 一种实体，两种加工来源

L2 只有一种实体。页面可以用“即时”或“统计”标签说明它由哪类加工产生，但不拆成“全局实体”和
“统计实体”两套对象。实体始终具有稳定身份、名称、类型、单位、值、质量、时间和来源证据。

### 5.2 实时与历史

实时列表显示当前值、单位、质量、更新时间和加工类型。每个已发布实体自动保存历史；用户从同一实体
进入历史趋势或明细。长时间范围自动使用分钟、小时或天聚合，用户只选择时间范围，不选择数据表。

### 5.3 来源和错误

点击实体先显示简明来源链：用了哪些 L0/L2 输入、经过什么加工、何时发布。帧号、摘要、配置修订和
完整来源证据放在“技术详情”。错误首先显示可执行的中文提示，例如“原始点位已 17 分钟未更新”；
`FRAME_PROCESSING_FAILED` 等内部代码只放在详情中。

## 6. 权限与发布

| 角色 | 权限 |
| --- | --- |
| 业主操作员 | 查看原始点位和实体的实时、历史及来源 |
| 实施工程师 | 配置绑定、加工规则、试算和发布当前设备 |
| 平台管理员 | 管理共享模板及其不可变修订 |

发布只有一个“检查并发布”动作。全部检查通过后原子切换配置；任何一项失败都不部分生效，设备继续使用
旧修订。数据库未提交前不推送页面、不触发告警/JDM、不控制设备。

## 7. 数据流

```text
设备/Neuron
   → 原始样本进入实时黑板
   → 统一节拍冻结不可变数据帧
   → 提交变化 L0
   → 按活动修订执行 L1 强类型 DAG
   → 原子提交 L0 latest、L2、历史、来源和 outbox
   → WebSocket 更新实时页
   → 告警、JDM、控制和 EMS 工作台消费 committed L2
```

页面首次打开或断线重连时读取完整终态快照和帧游标，随后只接收提交后的增量。实时展示不以持续轮询
数据库 latest 表为主链，历史查询才按时间范围读取数据库。

## 8. 最小验收闭环

未参与开发的实施工程师应能在一个真实或模拟 PCS 节点上完成：

1. 看见 L0 当前值、质量、来源和 7 天历史；
2. 选择推荐模板，处理少量歧义绑定，并通过在线试算；
3. 发布后看见即时和统计 L2 的当前值、历史及简明来源；
4. 更换同类品牌时只调整模板和输入绑定，L2 身份及上层引用不变；
5. 制造点位缺失、类型错误或试算错误时，发布被阻止且旧修订继续工作；
6. 告警、JDM、控制和工作台只能选择已提交 L2，不能绕过 L2 直接读 L0。

## 9. 明确不做

- 不增加 L3、独立统计实体系统或独立设备模板；
- 不把实时与历史复制成不同点位或实体；
- 不提供 SQL、任意脚本、万能表达式或第二套规则引擎；
- 不把哈希、修订、帧号和内部错误码放在普通用户首屏；
- 不复制 AWS IoT SiteWise 的云端模型层级和任一输入到达即混用其他最新值的 Transform 触发语义；
- 不扩展自由页面设计器、多租户、Redis、Kafka 或新微服务。

## 10. 设计依据与优先级

本规格细化核心架构总纲的用户操作面，不改变已确认的黑板、统一节拍、不可变帧、质量优先、来源证据
和提交后可见语义。AWS IoT SiteWise 仅作为外部参考：Measurement、Transform、Metric 与统一
Property 的做法支持“一种对象同时提供当前与历史、统计只是加工方式”的结论；ZiZu 不复制其云端
复杂度和异步混拍语义。

发生冲突时的阅读优先级是：核心架构总纲 → 最新 Accepted ADR → 本规格 → 历史界面或原型文档。
