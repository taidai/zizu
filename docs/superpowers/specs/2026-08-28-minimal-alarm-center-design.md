# 最简告警中心设计

## 1. 目的

让实施工程师不修改源码或 SQL，只用一个入口完成告警配置；让操作员一眼看懂当前发生了什么并完成
确认。复用已经部署的 committed L2 告警运行内核，不重写状态机，不增加新的消息通道、工作流或基础设施。

成功标准只有两条：

1. 实施工程师能够独立完成“选择 L2 → 设置规则 → 试算 → 发布”；
2. 操作员能够独立完成“查看活动告警 → 确认已知悉 → 查看自然恢复”。

## 2. 唯一入口

左侧菜单只保留一个“告警中心”。页面只有两个主视图：

```text
告警中心
├─ 当前告警
└─ 告警规则
```

“告警配置”不再作为独立菜单；JDM/规则引擎不再提供新建告警或故障映射入口。操作员只能进入“当前
告警”，工程师和管理员可以进入“告警规则”。

## 3. 当前告警

### 3.1 顶部摘要

只显示三个数字：活动告警、未确认、严重告警。计数来自统一 `t_alarm_events`，不混入旧告警表或历史
总数。

### 3.2 告警列表

一条告警默认只显示：

```text
等级｜节点/设备｜故障名称｜发生时间｜持续时间｜未确认/已确认｜确认按钮
```

默认查看活动告警；“查看历史”筛选已恢复事件。列表按“未确认优先、等级优先、发生时间倒序”排列。
页面可见时沿用简单 HTTP 轮询，不新增 WebSocket。UUID、帧号、配置修订、L2 事件、质量、来源证据和
审计 ID 放进可展开详情。

### 3.3 确认与恢复

“确认已知悉”只记录当前用户和时间，不要求填写说明，不提供“确认全部”。确认不关闭告警；只有新的
GOOD committed L2 满足恢复条件，告警才能自然恢复。页面不得提供人工恢复按钮。

## 4. 告警规则

### 4.1 规则列表

默认只显示：规则名称、应用设备数、规则数量/最高等级、启用状态，以及“编辑、复制、启用/停用”。
规则组、修订、稳定标识、摘要、幂等键和审计证据不作为普通表单字段，只在技术详情中只读展示。

启用/停用在界面上是一次操作；后端仍创建不可变修订并经过同一配置栅栏、旧帧/outbox 排空和原子
发布。数据库提交成功后开关才改变，失败时保持原状态并显示可读原因。规则内容编辑仍进入下述配置
流程，不能逐字段立即生效。

### 4.2 新增或编辑

用户只完成三步：

1. **选择实体**：从真实节点树搜索和批量勾选 L2，显示当前值、质量、单位和更新时间；混合不兼容的
   数据类型或单位时阻止继续；
2. **填写规则**：界面按 L2 数据类型自动选择数值、状态或故障码表单；
3. **试算、预览并发布**：用户输入测试值查看结果，确认中文变更摘要后发布。

“新增几条、修改几条、停用几条”必须用中文展示。内部继续复用现有版本化规则组、配置计划、摘要、
幂等 apply 和 `ConfigurationRuntimeGate`；这些不是额外的用户步骤。

## 5. 三类规则

### 5.1 数值

表单句式固定为：

```text
当 [实体] [比较符] [触发值] 持续 [时间]，产生 [等级] 告警；
当值 [比较符] [恢复值] 持续 [时间]，自动恢复。
```

触发值、恢复值和两个持续时间均可见；持续时间提供“立即、3秒、10秒、30秒”和自定义。系统校验
恢复方向，不猜测通用百分比。新数值规则默认触发 3 秒、恢复 3 秒。

### 5.2 状态

BOOL、ENUM 或普通 STRING 使用“等于/不等于某状态”配置，恢复条件必须明确。新状态规则默认立即触发、
恢复 3 秒。

### 5.3 多故障码

L1 负责把品牌原始码加工为稳定的 L2 `CODE_SET`；告警只识别标准码。用户在告警规则中维护：

```text
代码｜故障名称｜等级
E30 ｜压缩机故障｜重要
E31 ｜风机故障  ｜警告
```

支持逐行填写和直接粘贴 Excel 三列，不建设独立文件导入系统。每个代码展开为一条稳定规则和一个独立
告警事件；同一帧出现 E30、E31 时产生两条事件，一个代码消失只恢复对应事件。独立“故障码映射表”
管理页不再作为产品入口。

## 6. 无副作用试算

试算调用后端与正式运行相同的条件匹配函数，只返回“会触发、会恢复或无变化”及原因。它不得写入告警
事件、配置、outbox 或设备，也不得在前端复制一套判断语义。非 GOOD、类型不符或单位不符返回明确拒绝
原因。

## 7. 运行数据流

```text
配置：选择 L2 → 填写规则 → 同语义试算 → 中文变更摘要 → 安全发布
运行：committed L2 → CommittedL2AlarmConsumer → AlarmRuntime → 告警事件
操作：当前告警 → 确认已知悉 → 新 GOOD L2 满足恢复条件 → 自然恢复
```

告警仍只消费 committed L2。不得重新引入 L0、MQTT、latest 查询、JDM 告警动作或旧 `t_alarms` 运行
入口。

## 8. 错误与空状态

- 没有活动告警时显示“当前运行正常”，工程师可进入告警规则；
- 没有规则时显示“创建第一条告警规则”，不展示空表格；
- 实体无 GOOD 实时值仍可配置，但试算和运行明确显示质量原因；
- 发布结果未知时不得显示成功，必须用原幂等键查询或重试；
- 计划过期、配置并发、规则冲突和栅栏失败都保持原配置不变。

## 9. 本轮明确不做

- 不做短信、邮件、声音、值班升级或外部通知渠道；
- 不做新的 WebSocket、消息中间件、服务或数据库超级表；
- 不做自由表达式、JDM 告警、万能规则编辑器或页面设计器；
- 不做独立故障码管理页、模板市场或复杂文件导入；
- 不做人工恢复、确认全部或直接数据库开关；
- 不执行设备写入，不修改控制链。

## 10. 验收

1. 菜单中只有一个告警入口，角色可见性正确；
2. 数值、状态和多故障码各完成一次选择、试算、预览和安全发布；
3. 批量实体发布只改变选中范围，中文摘要与实际 add/update/delete 一致；
4. 试算与 `AlarmRuntime` 对相同输入产生相同判断且零持久化副作用；
5. 两个同时存在的故障码产生两条事件，并可分别确认和恢复；
6. 重放同一 committed frame 不重复产生事件，坏质量不制造假告警或假恢复；
7. 一条真实或受控 L2 数据完成触发、确认、自然恢复，页面名称和设备路径可读；
8. 后端完整测试、显式 PostgreSQL 告警测试和前端生产构建通过；
9. 1 号机保持 host network、`/dev/mqueue`、healthy、restart=0，不执行设备写入或 Caddy/TLS。
