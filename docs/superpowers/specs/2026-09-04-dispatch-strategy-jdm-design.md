# ZiZu 调度策略（JDM）专项规格

## 1. 目标

本规格把 ZiZu 的 JDM 能力收口成实施工程师能直接使用的“调度策略”：工程师不修改源码、不写 SQL，
只需选择 L2 全局实体、填写调度条件和目标值、试算、发布并启用，就能让策略经过统一安全控制入口驱动
设备。首个参考配置是光储站常见的“2 充 2 放”，首个真实设备闭环使用 PCS 的“最大放电功率限值”做
小幅、安全、可恢复的验证。

```text
committed L2 / 固定节拍 → 调度策略 → GoRules JDM → 控制意图 → 统一控制 → 设备 → L2 回读
```

用户只需要理解“调度策略”。JDM 是策略内部唯一的决策执行语义，不再作为另一套并列产品概念。

## 2. 当前基线与必须修正的缺口

当前代码已经具备 GoRules 编辑器、无副作用试算、committed-L2 帧消费者、JDM 执行事实以及统一控制
命令底座，但尚不能作为可交付的自动调度闭环：

1. `t_rules` 直接原地修改并用 `enabled` 同时表达保存和运行，没有草稿、不可变发布修订和安全切换；
2. 运行时只从当前帧的 `l2_changes` 取输入，未变化但仍有效的必需 L2 会被误判缺失；
3. `gorules_adapter` 同时支持标准 JDM、简化 `{when, actions}` 和 AST fallback，存在多套执行语义；
4. 动作仍可表达告警等旁路，尚未收窄为统一控制能够接收的安全意图；
5. 每帧执行都会写 `t_jdm_executions`，无变化时仍会产生不必要的数据库写入；
6. 没有共用的固定节拍入口、活动策略所有权、控制意图 outbox、失败锁定和完整回读闭环；
7. 页面面向通用规则图，普通实施工程师无法快速配置并看懂“2 充 2 放”。

本规格在已有 FastAPI、PostgreSQL/TimescaleDB、GoRules、committed L2 和统一控制运行时上收口，不新建
微服务，不引入 Redis、Kafka、Cron 系统或第二套规则引擎。

## 3. 范围与明确不做

### 本次交付

- 一个产品入口：“调度策略”；
- 数据变化和固定节拍两种触发方式，共用同一个运行时；
- 标准 GoRules JDM 的试算与正式执行；
- 草稿、发布、启用、停用和不可变修订；
- 一个可直接填写的“2 充 2 放”起始模板；
- 只读取 committed L2，只输出有序 `SET(L2, 目标值)` 控制意图；
- 控制意图提交后进入现有统一控制、设备写入和 L2 回读；
- 一张 TimescaleDB 超级表保存关键策略事件；
- 自动化验收、无头浏览器验收和一次真实 PCS 小幅设定值闭环。

### 不做

- 不做用户可见的 Cron 表达式、Cron 管理器或独立调度服务；
- 不做“简单模式/高级模式”两套模型，也不做模型互转或反编译；
- 不做任意 Python/JavaScript、AST fallback、第二套表达式执行器；
- 不允许 JDM 直接写 L0、Neuron 地址、MQTT、HTTP、告警表或设备；
- 不支持等待、循环、脉冲、toggle、脚本动作或流程编排；
- 不做历史回放试算、全站大快照、每拍执行日志或通用模板市场；
- 不把固定节拍变成精确到秒的一次性定时任务；
- 不在本次真实设备验收中冒充已经完成完整“2 充 2 放”能量调度。

## 4. 领域对象与状态

### 4.1 调度策略

调度策略是稳定的业务身份，保存名称、说明和当前状态。它不直接保存可变运行规则；具体输入、JDM、
输出、触发方式和场站时区全部冻结在不可变修订中。

### 4.2 策略修订

策略每次编辑只产生草稿。发布把草稿校验并冻结为新的不可变修订；修改已启用策略时，旧修订继续运行，
新内容不会偷跑。发布成功也不等于启用。

### 4.3 策略启用

启用把一个已发布修订变成当前运行修订。新修订替换旧修订前，必须等待旧修订没有未完成控制；随后原子
切换活动指针。只有 `engineer` 能发布、启用、停用和解除失败锁定。

配置生命周期、启用状态和运行健康必须分开表达，不能塞进一个互斥状态字段：修订分别是 `DRAFT` 或
`PUBLISHED`；策略启用状态是 `ENABLED` 或 `DISABLED`；已启用策略的运行健康是 `READY`、`BLOCKED`
或 `FAILED`。因此一个策略可以在旧发布修订正常运行时，同时保留一个新草稿。`BLOCKED` 表示当前输入
或安全前提不满足，条件恢复后可在下一次触发重新求值；`FAILED` 表示动作已经失败并锁定，必须由工程师
处理原因后显式解除，不能每分钟无限重试。

### 4.4 控制意图

控制意图是 JDM 已经决定、但尚未写设备的有序 `SET` 请求。它只包含目标 L2、期望值、策略与修订证据、
输入快照证据、顺序号和幂等身份；物理地址、Neuron 路由、权限、限值、联锁、冷却和回读仍由统一控制
运行时负责。

## 5. 用户界面与配置流程

主导航把现有“规则引擎/JDM”统一显示为“调度策略”。首屏是策略列表，显示：名称、触发方式、控制目标、
发布版本、运行状态、最近求值、期望值/实际值和最近动作结果。

普通实施工程师的最短路径固定为：

```text
新建策略 → 选择“2充2放” → 绑定 L2 输入和可控 L2 → 填时间表
         → 试算 → 发布 → 启用 → 查看运行记录 → 停用
```

“2 充 2 放”页面直接呈现一张决策表，至少包含本地开始时间、本地结束时间、动作、功率目标、SOC 下限和
SOC 上限。时间段不得重叠；跨午夜区间拆为两行；必须配置“其他时间”的安全目标，平台不猜测这个值。
首个模板随产品内置，不建设模板 CRUD；出现第二个经过真实交付验证的重复需求后，再增加第二个模板。

这张表本身就是标准 JDM 中的决策表节点，不另存一份“简易规则”。需要复杂需求的工程师可以直接打开
同一份 JDM 完整规则图继续编辑；页面不在两种格式之间转换。

“试算”默认读取当前一份真实输入快照，也允许临时覆盖输入。结果必须同时显示：绑定的 L2 值、质量、
数据时间、命中的规则行、决策结果和将要产生的控制意图。试算使用正式 GoRules JDM，但永远不创建控制
意图、不写设备。

人工控制同一目标前，必须先停用拥有该目标的自动策略。页面不再创造“手动/自动”两套运行模式；设备
本地保护、急停和 PLC/PCS 安全逻辑始终高于 ZiZu。

## 6. 运行架构与模块接口

策略能力收口在一个深模块 `StrategyRuntime` 后面。调用方只需要提交触发或发起试算，不需要理解 JDM、
快照、幂等、事件记录和 outbox 的内部步骤。

```text
committed L2 变化 ─┐
                   ├→ StrategyRuntime
共享固定节拍 ─────┘     │
                         ├─ 冻结策略绑定的 L2 一致快照
                         ├─ 执行唯一 GoRules JDM
                         └─ 事务提交决策、关键事件、控制意图 outbox
                                                │ 数据库提交后
                                                ▼
                                      ControlIntentDispatcher
                                                │
                                                ▼
                                      ControlCommandRuntime
                                                │
                         L2 回读确认 ← Neuron ← 唯一 L0 写点
```

外部接口保持最小：

- `simulate(revision, snapshot, overrides)`：返回决策路径、结果和拟产生意图，无副作用；
- `evaluate(strategy_id, trigger)`：得到确定快照、执行 JDM，并原子保存结果与待分派意图；
- `dispatch(intent_id)`：提交后把待分派意图交给现有 `ControlCommandRuntime`；
- `disable(strategy_id)`：停止新求值并取消尚未分派的意图。

`StrategyRuntime` 与 `ControlCommandRuntime` 是两个清晰的 seam：前者只回答“现在想做什么”，后者统一
回答“这个动作现在能不能安全执行，并且现场是否真的完成”。不再为 GoRules、固定节拍或模板建立新的
公开模块层。

## 7. 触发和一致输入快照

### 7.1 数据变化触发

策略绑定的任一 L2 在 committed frame 中发生值或质量变化时触发。触发帧只负责提供截止位置，不要求
所有必需输入都恰好在这一帧变化。

### 7.2 固定节拍触发

单站进程内使用一个共享分钟节拍，默认每分钟巡检一次所有固定节拍策略。它不是独立 Cron 系统，也不
保证进程停机期间逐分钟补跑；重启后在下一拍按当前时间和当前现场状态重新求值。业务时间窗保存在 JDM
决策表中，平台只提供一个保留的、只读的“场站本地时间”输入。时间按 UTC 保存，按策略冻结的场站时区
解释。

### 7.3 一致快照

每次触发先固定 `configuration_revision`、截止 `frame_sequence` 和求值时间，再读取该策略声明的全部
L2 输入在截止帧及以前的最新 committed 值。各输入不要求来自同一个物理采样帧，但必须满足各自的
`GOOD` 质量和新鲜度要求。任何必需输入缺失、非 GOOD、过期、来自错误配置修订或类型/单位不符时，
整次策略 fail closed，不执行 JDM、不产生控制意图。

这样既避免“等待全站所有数据同一时刻到齐”，也避免当前实现只看 `l2_changes` 而把未变化的有效输入
误判为缺失。固定节拍即使没有新数据帧也能求值，但只能使用仍在新鲜度范围内的 committed L2。

两种触发共用同一评估入口。幂等身份由策略修订、触发类型和截止帧/节拍时间共同确定；重复投递只能
返回原结果，不能重复创建控制。

## 8. 唯一 JDM 与动作契约

正式执行和试算只接受标准 GoRules JDM，由同一版本的 zen-engine 求值。缺少 zen-engine、模型无效或
求值异常都明确失败；不得回退到 AST、`{when, actions}` 或其他解释器。

JDM 输入只有：

- 明确绑定的 committed L2 强类型值；
- 平台保留的场站本地时间；
- 试算时显式标记的临时覆盖值。

JDM 可以产生普通决策结果和零个或多个有序控制意图。唯一允许的外部动作形态是：

```text
SET(可控 L2 实体实例, 强类型目标值)
```

每个动作必须具有稳定 `action_id`，目标必须在发布时确定绑定并通过类型、单位、可控性和唯一 L0 写点
校验。禁止运行时按名称猜目标，也禁止动作携带节点、Tag、寄存器、topic、payload、HTTP 地址、告警
内容、等待或循环。

多个动作严格按声明顺序执行；前一个动作取得新 committed L2 回读确认后，才允许分派下一个。任一动作
最终失败，余下动作停止，不自动倒序回滚。

## 9. 发布、所有权与安全栅栏

发布前必须一次性校验：

- 标准 JDM 结构和表达式可编译；
- 全部输入和输出 L2 存在，类型、单位和新鲜度契约明确；
- 输出 L2 可控，并确定映射到唯一已确认 L0 写点；
- 时间窗不重叠、跨午夜已拆分、“其他时间”已填写；
- 输出值在控制策略限值内；
- 依赖和输出不存在循环或自触发歧义；
- 基础配置修订号和内容摘要未被并发修改。

一个可控 L2 同一时刻只能被一个已启用自动策略拥有。该约束由数据库唯一性和发布/启用事务共同保证，
不能靠页面提示。策略可以有多个目标，但任一目标已有主人时整次启用失败，不能部分启用。

新修订切换复用现有配置栅栏：停止接收旧修订新触发，等待旧修订已提交意图和在途控制收敛，再原子
切换活动修订。设备分派前必须再次复核策略仍启用、修订仍活动、目标所有权未变化、来源配置修订有效，
以及统一控制的质量、限值、联锁、冷却和权限；任一条件变化都取消意图，零设备写入。

高风险目标继续服从统一控制的现行二次确认/授权契约。调度策略本身不能伪造或绕过高风险授权；本规格
不恢复已经删除的解决方案包或旧 `ems_policy` 运行旁路。

## 10. 决策、意图与重试语义

策略求值后先比较“本次期望值”和目标 L2 的当前实际值：

- 期望未变化且实际值已在容差内：不创建命令；
- 期望未变化但实际值发生漂移：若没有在途动作或失败锁定，创建一次纠偏意图；
- 已有相同在途意图：返回原意图，不重复创建；
- 已处于失败锁定：只显示失败，不按每分钟节拍重复写设备。

决策事实、关键策略事件和控制意图 outbox 必须在一个数据库事务中提交。事务未提交时，dispatcher 不可
见，也不得控制。数据库提交失败时不产生设备动作；下一次触发可安全重新计算。提交后进程崩溃时，重启
从未完成 outbox 恢复。

一个动作最多尝试 3 次。每次尝试前都重新执行活动修订、来源帧、目标所有权、质量、限值、联锁和冷却
校验，并使用由意图 ID 与尝试序号导出的稳定幂等键提交统一控制。第三次仍未回读确认后，动作和策略
进入 `FAILED`，停止剩余动作并产生告警；不得无限重试或自动回滚。

停用策略时立即停止新求值，并取消尚未交给统一控制的意图。已经下发设备的命令继续完成回读、失败或
超时记录，然后策略停止。

## 11. 最小数据结构

目标数据结构只保留四类策略数据，不按策略或实体分表：

| 数据对象 | 作用 |
|---|---|
| 调度策略 | 稳定身份、显示信息、当前活动修订和运行状态 |
| 不可变策略修订 | 触发方式、时区、标准 JDM、L2 输入/输出绑定、摘要和发布证据 |
| 控制意图 outbox | 有序 `SET` 意图、状态、尝试次数、幂等身份及关联控制命令 |
| 策略事件超级表 | 决策变化、意图创建、安全阻断、原因变化、恢复和最终失败 |

策略事件超级表只记录有业务意义的变化：决策改变、控制意图创建、首次进入阻断、阻断原因改变、恢复和
失败。固定节拍得到相同决策且没有动作时不写记录；同一阻断持续存在时也不每分钟重复写。最近期望值、
最近求值、所依据的实际值证据和失败锁定保存在策略当前状态中，不作为时序日志反复追加；页面展示的
当前实际值仍以最新 committed L2 为准，策略状态不成为第二份实时真相。

每条关键事件至少保存策略与修订、触发身份、截止帧、配置修订、绑定 L2 的值/质量/时间、JDM 结果、
控制意图摘要和关联 `control_command_id`。详细的权限、限值、下发、重试和回读仍只保存在现有控制命令
记录中，策略表不复制第二份控制审计。

现有 `t_rules`、`t_rule_templates`、简化规则格式和逐帧 `t_jdm_executions` 不再作为新调度策略的运行
语义。实施迁移时，兼容的 control/linkage 内容最多转换为未启用草稿；无法确定绑定的旧内容保持不可
执行，不建立运行期 fallback。告警等历史旧类型不得重新并入调度策略。

## 12. 失败处理

| 场景 | 必须结果 |
|---|---|
| 必需 L2 缺失、BAD、UNCERTAIN 或 STALE | `BLOCKED`，不求值、不控制；原因改变和恢复各记一次 |
| JDM 无法编译或运行失败 | 发布阻断或运行 `FAILED`，告警并等待人工处理 |
| 数据库事务失败 | 零控制；下次触发重新计算 |
| 提交后、分派前崩溃 | outbox 重启恢复，同一意图不重复 |
| 重复帧或重复节拍 | 命中幂等结果，不重复控制 |
| 实际值偏离未变化的期望值 | 无失败锁定/在途动作时纠偏一次 |
| 控制写入或回读失败 | 每次重验，最多 3 次；随后锁定失败并停止序列 |
| 配置或活动修订在分派前变化 | 取消旧意图，零设备写入 |
| 策略停用时仍有待分派意图 | 取消待分派；已下发命令只完成收尾记录 |
| 进程重启 | 恢复活动修订、当前状态和已提交 outbox；不补跑停机期间每分钟任务 |
| ZiZu 与现场失联 | 不产生新控制；设备/PLC/PCS 本地 watchdog 承担最终失效安全 |

## 13. 验收标准

### 13.1 自动化验收

必须通过公开 seam 和真实 PostgreSQL 覆盖：

1. 时间窗边界、必填“其他时间”、重叠拒绝、跨午夜拆分和 SOC 上下限；
2. 绑定输入在不同帧更新时，仍按同一截止帧得到完整一致快照；
3. 缺失、BAD、UNCERTAIN、STALE、旧配置修订和类型/单位错误均零控制；
4. 数据变化和固定节拍使用同一个 GoRules 执行结果；试算与正式执行结果一致且试算无副作用；
5. 相同触发重放、进程重启和 outbox 重放不产生重复控制；
6. 期望不变且实际到位时无动作，实际漂移时只纠偏一次；
7. 同一目标的策略所有权冲突整次拒绝；修改已启用策略不影响旧修订，安全切换后才使用新修订；
8. 数据库失败、JDM 失败、控制失败、三次重试和失败锁定都产生确定结果；
9. 停用时待分派意图取消，已下发命令完成收尾；
10. 持续相同决策和相同阻断不产生每分钟日志，原因变化与恢复各留一条事件；
11. 代码中不存在新策略走 AST、简化规则、L0、MQTT、HTTP 或直接 Neuron 写入的旁路。

### 13.2 真实 PCS 小幅闭环

使用真实 PCS 点位 `en9_pcs/cmd` 的“最大放电功率限值”，地址 `1!420601`，`INT16`、小数位 `0.1`。
执行前重新读取并确认现场当前值仍为 `156.8 kW`、质量 GOOD、控制绑定唯一、联锁满足且现场允许测试。

```text
156.8 kW → 调度策略 SET 156.7 kW → 新 committed L2 回读确认
         → 调度策略 SET 156.8 kW → 新 committed L2 回读确认恢复
```

任一步不满足门禁或未在超时内回读时立即停止后续动作，不扩大变化量。这个验收只证明“策略决定 → 统一
控制 → 真实设备 → L2 回读”的安全闭环，不宣称已经完成真实充电和放电调度。

### 13.3 无头浏览器验收

部署后用无头浏览器走通：

```text
新建策略 → 填写/绑定 2充2放表 → 试算 → 发布 → 启用
         → 查看关键事件和控制回读 → 停用
```

同时沿平台主干复核“节点树 → L0 → L1 → L2 → 告警 → 调度策略”，确认页面只使用 L2、没有控制旁路，
浏览器控制台无错误。自动化测试、数据库证据、控制命令和真实回读必须相互对应；页面能打开不算完成。

## 14. 完成定义

只有以下条件全部满足，才能宣称调度策略首个纵向切片完成：

- 普通实施工程师能在一个页面完成创建、试算、发布、启停和查看结果；
- 正式运行只有标准 GoRules JDM 一套语义；
- 两种触发都读取同一截止帧上的完整绑定 L2 快照；
- 决策提交前无设备动作，提交后可恢复且幂等；
- 所有自动动作都经过统一控制、最多三次尝试并以新 L2 回读为成功依据；
- 关键事件超级表没有逐拍无效写入；
- 自动化、无头浏览器和真实 PCS 小幅闭环全部留下可核对证据。

本规格不等于完整光储充 EMS 已交付。后续真实“2 充 2 放”还必须绑定经过现场确认的功率设定、运行模式、
SOC/保护联锁和本地失效安全，并单独完成充放电验收。
