# ZiZu 配置式交付 v1 规格

> 状态：主测试缝已确认，已拆分为 GitHub Issues #1–#19
> GitHub 票据：#1–#19（仓库默认标签 `enhancement`）
> 日期：2026-08-12

## Problem Statement

ZiZu 已具备 Neuron/NanoMQ 设备接入、TimescaleDB 时序存储、设备模板、实体、告警、规则和设备写入等基础能力，但这些能力仍是分散的数据库记录、管理页面和运行路径，无法证明实施工程师可以通过简单配置稳定交付一套工业控制系统。

以光储充 EMS 为例，当前交付存在五类根本问题：配置资产不能作为一个版本化产品安装和升级；多台同类设备缺少稳定的实体实例语义且绑定可能静默选错源；告警确认、恢复和计数语义不一致；人工与自动控制存在旁路且写成功没有现场回读证据；生产接口、安全制品和验收过程无法形成可审计、可重现的交付证明。

因此，“页面上已有功能”不等于“配置式交付成立”。平台需要让未参与开发的实施工程师，在已有协议驱动和设备模板时，不修改源码、不直接操作数据库、不依赖临时脚本或开发人员口头指导，在四小时内完成一个新站点，并让机器验收清单证明设备、数据、告警、控制、策略、审计和发布状态均交付就绪。

## Solution

ZiZu v1 以版本化的**解决方案包**作为工业控制系统的交付单位。光储充 EMS 参考解决方案包使用声明式清单组合节点、设备、实体定义与实例槽位、绑定规则、告警、控制、基础策略、EMS 运行工作台和机器验收清单。实施工程师通过安装向导填写强类型参数并解决现场绑定，平台在安装前完成 Schema、兼容性、安全和确定性检查，展示差异计划后幂等安装。

平台将运行语义收口到三个深模块：实体实例提供唯一、稳定的业务对象；告警状态机只由现场观测触发和恢复；控制命令统一承接人工与自动写入，并以写后回读确认作为成功判据。生产环境默认认证所有业务 REST API 和 WebSocket，服务端执行 admin、engineer、operator 权限及命令级控制策略。

平台和解决方案包独立版本化。正式部署只使用带 digest 的固定版本多架构镜像，并生成包含平台、镜像、数据库 Schema、解决方案包和站点配置版本的发布锁定。验收服务通过与真实实施流程相同的公开 API 执行清单，生成逐项证据和总体结论。光储充 EMS 参考交付最终由独立实施工程师完成四小时计时试验。

## User Stories

1. 作为实施工程师，我希望浏览可安装的光储充 EMS 解决方案包，以便从受支持的交付基线开始项目。
2. 作为实施工程师，我希望看到解决方案包版本、平台兼容范围和资产摘要，以便在安装前判断是否适用。
3. 作为实施工程师，我希望平台在导入时校验解决方案清单和全部引用资产，以便错误包不会污染站点。
4. 作为实施工程师，我希望安装向导只询问参数契约声明的现场差异，以便无需理解平台内部表结构。
5. 作为实施工程师，我希望每个参数显示类型、单位、是否必填、默认值和允许范围，以便减少现场录入错误。
6. 作为实施工程师，我希望敏感参数只选择 Secret 引用，以便凭据不会进入解决方案包、站点导出或报告。
7. 作为实施工程师，我希望安装前查看将新增、修改、保留和冲突的配置，以便批准变更前理解影响。
8. 作为实施工程师，我希望重复执行同一个安装计划不会产生重复资产，以便安装失败后能够安全重试。
9. 作为实施工程师，我希望一个 ZiZu 实例只对应一个站点，以便首版运维和权限边界保持清晰。
10. 作为实施工程师，我希望从实例槽位创建多台 PCS、BMS、逆变器、充电桩和电表，以便复用标准语义而不复制模板代码。
11. 作为实施工程师，我希望每个实际设备拥有稳定的实体实例 ID，以便规则、告警、页面和控制都引用同一个对象。
12. 作为实施工程师，我希望系统自动列出每个必需实体实例的候选点位，以便高效完成绑定。
13. 作为实施工程师，我希望唯一候选能够按包内明确规则预选，以便减少重复劳动。
14. 作为实施工程师，我希望缺失候选明确显示为缺口，以便在交付前补齐设备或映射。
15. 作为实施工程师，我希望多个候选明确显示为歧义并阻止交付，以便系统不会按优先级或创建顺序选错数据源。
16. 作为实施工程师，我希望主备来源通过显式故障切换策略配置，以便来源切换是可见和可测试的。
17. 作为实施工程师，我希望配置实体量纲、数据类型和读写方向得到校验，以便错误的物理含义不能进入运行态。
18. 作为实施工程师，我希望为实体实例配置告警定义、持续时间、迟滞和恢复条件，以便告警符合现场设备行为。
19. 作为业主操作员，我希望一次持续故障表现为一个告警事件，以便采样频率不会制造海量重复告警。
20. 作为业主操作员，我希望确认活动告警只表示我已知悉，以便确认操作不会伪造设备恢复。
21. 作为业主操作员，我希望告警只在现场恢复条件满足后进入已恢复，以便运行记录可信。
22. 作为业主操作员，我希望看到告警的触发、确认、恢复和通知历史，以便追溯事故过程。
23. 作为实施工程师，我希望 MQTT、标签和实体告警进入同一个状态接口，以便不同来源具有一致语义。
24. 作为实施工程师，我希望设置通知节流策略，以便告警持续期间不会产生通知风暴。
25. 作为业主操作员，我希望从 EMS 运行工作台发起被授权的控制命令，以便安全操作现场设备。
26. 作为策略引擎，我希望通过与人工相同的控制命令入口执行动作，以便自动控制不能绕过安全检查。
27. 作为平台管理员，我希望按角色和具体命令限制控制权限，以便最小权限原则落实到服务端。
28. 作为业主操作员，我希望高风险控制提示二次确认，以便降低误操作概率。
29. 作为实施工程师，我希望控制命令在下发前检查类型、范围、联锁、幂等键和冷却时间，以便危险或重复指令被拒绝。
30. 作为业主操作员，我希望看到命令处于已受理、校验通过、已下发或等待回读，以便理解实际进度。
31. 作为业主操作员，我希望只有现场回读满足期望值、容差和超时才显示成功，以便接口写入成功不被误认为设备执行成功。
32. 作为实施工程师，我希望命令失败、超时和结果不一致保留原因和证据，以便现场诊断。
33. 作为审计人员，我希望人工和自动控制记录相同的发起者、授权、输入、联锁、下发和回读轨迹，以便责任可追溯。
34. 作为业主操作员，我希望使用固定的 EMS 运行工作台查看设备分组、关键指标、趋势、告警和控制，以便交付界面一致且易培训。
35. 作为实施工程师，我希望通过解决方案包配置工作台导航、分组、指标、趋势和入口可见性，以便适配站点而不编写前端代码。
36. 作为平台管理员，我希望工作台只使用平台允许的组件和引用实体实例，以便配置不能注入任意代码。
37. 作为实施工程师，我希望基础策略在启用前验证输入完整性并支持仿真，以便避免带缺失数据上线。
38. 作为平台管理员，我希望生产模式默认要求所有业务 REST API 和 WebSocket 认证，以便遗漏配置不会暴露控制面。
39. 作为开发人员，我希望只能显式开启开发匿名模式并看到醒目警示，以便测试便利不会被误带入生产。
40. 作为平台管理员，我希望管理用户及 admin、engineer、operator 角色，以便职责分离。
41. 作为实施工程师，我希望升级前比较旧解决方案包、当前站点配置和新解决方案包，以便站点覆盖得到保留。
42. 作为实施工程师，我希望升级冲突必须逐项解决才能执行，以便新包不会静默覆盖现场调整。
43. 作为实施工程师，我希望升级失败可回到上一个可验证发布锁定，以便现场恢复有确定基线。
44. 作为平台管理员，我希望每次部署记录镜像 digest、平台版本、数据库 Schema、包版本和站点配置版本，以便实际运行内容可证明。
45. 作为开源用户，我希望获得多架构、固定版本、可校验的发布制品，以便在 x86_64 和 ARM64 环境复现部署。
46. 作为开源贡献者，我希望解决方案包格式、EMS 参考资产、部署流程和验收测试公开，以便可以审查和扩展平台。
47. 作为客户，我希望现场凭据、参数和真实拓扑不进入公开仓库，以便项目敏感信息受到保护。
48. 作为实施工程师，我希望一键运行解决方案包携带的机器验收清单，以便判断站点是否交付就绪。
49. 作为实施工程师，我希望验收检查设备在线、绑定唯一、数据新鲜、告警生命周期、控制回读、策略仿真和审计，以便覆盖完整运行闭环。
50. 作为客户，我希望收到带版本、执行时间、逐项结果和证据的交付报告，以便验收结果可归档和复查。
51. 作为产品维护者，我希望由未参与开发的实施工程师完成四小时独立交付试验，以便“简单配置即可交付”得到真实证据。
52. 作为产品维护者，我希望试验记录总时长、人工步骤、自动步骤、失败点和配置覆盖率，以便持续降低交付成本。

## Implementation Decisions

### 1. 产品与版本边界

- 首版为单实例单站，不实现租户、跨站聚合或站点间权限；数据模型只预留未来平滑引入站点标识的空间。
- 平台核心、解决方案包格式、光储充 EMS 参考资产、部署和验收测试开源；客户参数、Secret、真实拓扑和商业服务不公开。
- 平台版本、解决方案包版本和站点配置版本相互独立。解决方案包使用语义版本，并声明支持的平台版本范围和 Schema 版本。
- 计费、工单、移动端、通用拖拽大屏不进入首版。

### 2. 解决方案包契约

- 解决方案包是可进入 Git 的声明式目录或其不可变归档，不是数据库备份，也不携带可执行应用代码。
- 根解决方案清单至少声明：Schema 版本、包标识、包版本、显示信息、平台兼容范围、资产清单及内容摘要、参数契约、升级元数据和验收清单引用。
- 资产类型至少包括：节点/设备模板、实体定义、实体实例槽位、绑定规则、告警定义、控制定义、基础策略、EMS 运行工作台和验收定义。
- 所有资产具有包内稳定 ID；跨资产引用使用稳定 ID，不使用数据库自增 ID、显示名或文件顺序。
- 参数契约至少支持字符串、整数、数值、布尔、枚举、地址/端口、持续时间和 Secret 引用；参数可声明单位、必填、默认值、范围、模式和说明。
- 敏感参数只能解析为运行时 Secret 引用。包导出、站点配置导出、差异预览、日志、审计和验收报告不得回显 Secret 值。
- 导入顺序为完整解析、Schema 校验、引用完整性、兼容性、安全约束、参数校验，任何失败均不改变运行配置。
- 包的上传、验证和安装是不同动作。未经验证的包不能安装；安装必须基于保存的不可变包摘要。

### 3. 安装、差异与升级

- 安装器先生成可审查的安装计划，再执行事务化或可补偿的幂等变更。计划包含新增、更新、保留、删除候选、冲突和阻断项。
- 首次安装以包默认值和站点参数实例化资产。实施工程师的明确修改记录为站点覆盖，并携带来源和修改时间。
- 升级采用旧包、当前站点配置、新包三方差异。未覆盖项跟随新包；站点覆盖默认保留；同一属性被包和站点同时改变时形成显式冲突。
- 删除已有运行引用、改变实体量纲/方向、放宽控制权限、改变告警恢复语义和丢失 Secret 引用属于高风险变更，必须阻止自动执行并要求工程师处理。
- 安装和升级失败不得留下对外可见的半安装配置；恢复后重复执行同一计划结果一致。
- 每次成功安装或升级生成不可变的站点配置版本和变更审计。

### 4. 实体定义、实体实例与绑定

- 实体定义描述标准业务语义、数据类型、单位、读写方向和适用设备类别；实体实例描述站点内实际对象并引用一个实体定义。
- 解决方案包通过实例槽位声明设备种类、数量参数、命名规则和必需实体集合；安装时生成稳定实体实例 ID。
- 规则、告警、控制、验收和 EMS 运行工作台只引用实体实例 ID。展示名可以改变，不影响引用。
- 每个必需的读实体实例在交付就绪前必须解析为一个确定主来源。零候选是缺失，多候选是歧义，两者均为阻断状态。
- 自动预选仅可使用包中可解释、确定性的匹配条件；匹配结果及理由必须出现在安装计划，禁止按优先级、创建时间或查询返回顺序静默选源。
- 主备来源属于单独、显式的故障切换策略，并提供当前来源及切换审计；不能通过多个同优先级绑定表达。
- 现有全局实体迁移时先生成预览：可唯一归属者转换为实例候选；多设备共享或多候选者必须人工解决；迁移完成前旧模型保持只读兼容。

### 5. 统一告警状态机

- MQTT、标签和实体来源先转成统一现场观测，再驱动相同的告警状态接口；来源适配器不得直接维护独立生命周期。
- 告警状态为 `normal`、`pending`、`active_unacknowledged`、`active_acknowledged`、`recovered`。一次连续现场条件对应一个告警事件。
- 触发条件持续达到配置时长后，由 `pending` 进入活动；条件提前消失则回到 `normal`。迟滞和恢复条件用于避免边界抖动。
- 确认只允许活动未确认进入活动已确认，记录操作者、时间和备注，不改变现场条件。
- 只有现场恢复条件满足才能进入已恢复。人工 API 不提供把仍活动告警直接恢复的能力。
- 通知由状态转换触发，并按告警定义节流；每次采样不得增加活动事件数量或重复发送无意义通知。
- 告警事件保存定义版本、实体实例、触发/恢复观测、状态转换和确认记录，以支持完整审计。
- 现有告警迁移保留历史为旧版只读记录；新的统一状态机从迁移切换点开始生成事件，禁止通过猜测重写历史现场状态。

### 6. 统一控制命令

- 页面、规则、策略和兼容 API 都只能创建控制命令，不得直接调用设备写接口。设备适配器只接受来自控制执行器的已授权下发请求。
- 控制命令至少包含：稳定命令 ID、幂等键、来源主体与来源类型、目标实体实例、期望值、数据类型、容差、超时、权限动作、联锁集合、冷却策略和关联审计 ID。
- 主流程状态为 `accepted`、`validated`、`dispatched`、`readback_confirmed`；终止状态为 `rejected`、`timeout`、`failed`、`mismatch`。所有转换持久化且单调，不允许终止后回到执行态。
- 校验按服务端权限、命令级策略、数据类型、上下限、设备可控性、运行联锁、持久冷却和幂等顺序执行；拒绝必须给出机器码与可读原因。
- 高风险命令可要求二次确认。确认令牌绑定主体、命令内容和短有效期，修改命令后必须重新确认。
- 下发成功只进入 `dispatched`。执行器在超时内观察声明的回读实体；满足期望值及容差才进入 `readback_confirmed`，未到达或相反状态分别进入超时或不一致。
- 冷却、幂等和命令状态必须持久化，服务重启不能绕过限制或丢失在途命令；重启后按状态恢复观察或安全终止。
- 兼容写入 API 在有限迁移窗口内转换为控制命令并返回命令 ID；不得继续返回易误解的同步“设备已成功”语义。

### 7. EMS 运行工作台与策略

- 首版提供由平台维护的固定 EMS 运行工作台，不允许运行包内任意前端代码。
- 解决方案包可配置导航、能源子系统/设备分组、KPI 实体引用、趋势实体集合与默认范围、告警入口和控制入口可见性。
- 工作台配置只能引用允许的组件类型和实体实例 ID；导入时校验组件属性、权限要求和引用完整性。
- 基础策略同样只引用实体实例，并通过统一控制命令产生动作。策略启用前必须通过输入完整性、单位和仿真用例校验。
- 光储充 EMS 首版策略集合至少覆盖已确认的基础场景，但具体调度算法可按独立 tracer ticket 逐步引入，不阻塞解决方案包骨架。

### 8. 身份、认证和授权

- 首版服务端角色为 `admin`、`engineer`、`operator`。admin 管理平台、用户、系统配置和包生命周期；engineer 管理设备、绑定、告警、策略和验收；operator 运行监控、确认告警和执行被授权控制。
- 权限基于明确动作而非页面名称；所有 REST、WebSocket 订阅和控制转换均在服务端验证。前端隐藏按钮只改善体验，不构成安全边界。
- 生产模式默认拒绝匿名业务访问，仅最小 liveness 探针匿名；readiness、配置、指标和调试信息按敏感度认证或限制网络范围。
- 开发匿名必须通过显式非生产配置开启，并在健康状态、日志和界面持续显示不安全标志；生产配置检测到匿名模式时启动失败。
- WebSocket 建连时认证，并在会话失效或权限撤销后终止；订阅内容遵守与 REST 相同的数据权限。
- 所有登录、权限拒绝、配置变更、告警确认、控制命令和验收运行进入统一审计轨迹。

### 9. 发布锁定、部署与回滚

- 平台正式发布提供 x86_64 和 ARM64 镜像清单，每个版本使用不可变标签和内容 digest；正式部署禁止 `latest` 和宿主机源码覆盖。
- 数据库迁移具有可查询的 Schema 版本，部署在服务切换前验证迁移路径、镜像架构、包兼容性和 Secret 引用。
- 每次成功部署生成发布锁定，至少包含平台版本、所有运行镜像 digest、数据库 Schema 版本、解决方案包版本、站点配置版本和生成时间。
- 运行健康信息展示发布锁定摘要，但不泄露 Secret 或内部拓扑。
- 回滚目标必须是已有、可验证的发布锁定；回滚前检查数据库迁移可逆性和站点配置兼容性。不可逆迁移必须使用向前恢复方案并在升级前明确阻断直接回滚。

### 10. 验收清单与交付报告

- 验收清单属于解决方案包的声明式资产。检查项具有稳定 ID、说明、前置条件、执行方式、超时、成功判据、严重级别和证据脱敏规则。
- 验收执行只通过与实施工程师相同的公开 API 和设备/协议边界，不直接访问数据库，不调用内部 Python 对象，不使用站点专用临时脚本。
- 必需检查至少覆盖：设备与协议网关在线、必需绑定完整且唯一、数据新鲜、历史落库、告警触发/确认/现场恢复、控制下发/回读、策略输入与仿真、权限拒绝、审计完整和发布锁定一致。
- 若控制链不可用（例如 Neuron REST 403），控制检查必须以明确的 `control_not_ready` 失败，整站不得标记交付就绪。
- 报告包含平台与包版本、站点配置版本、发布锁定、执行主体、开始/结束时间、逐项状态、机器码、脱敏证据和总体结论。
- 必需项任何失败或阻断均使总体结论失败；允许可选项跳过，但必须记录理由。
- 报告是不可变审计记录，可导出为机器可读格式和面向客户的可读格式，两者来自同一次验收运行。

### 11. 四小时独立交付试验

- 试验参与者必须是未参与 ZiZu 开发的实施工程师；环境为干净备用实例，设备可使用公开的协议模拟器或真实测试设备。
- 计时从获得公开文档、发布制品和解决方案包开始，到机器验收报告全部必需项通过结束。
- 只允许公开文档、发布制品、解决方案包、产品界面和公开 API。修改源码、直接数据库/SQL、一次性脚本或开发人员口头指导均判失败。
- 除四小时上限外，至少 90% 的点位、实体、告警和策略必须通过模板、包和界面/API 配置完成；手工步骤、阻塞时间和失败原因必须记录。
- 第一次失败不是隐藏或放宽标准的理由，而是进入下一轮产品改进的事实证据；修复后使用全新环境重新试验。

### 12. 实现顺序与兼容窗口

- 第一条 tracer bullet 先建立最薄的完整公开交付路径：导入只含平台 liveness 验收项的最小解决方案包、生成安装计划、幂等安装并输出机器验收报告。它不以模拟实现绕过公开接口，但暂不同时承担设备、实体、告警和控制迁移。
- 随后以独立纵向切片依次加入参数与 Secret、单设备实体实例、实时数据验收、统一控制、统一告警、工作台、基础策略、三方升级、不可变发布和完整 EMS 参考资产；每一步扩展同一端到端验收缝。
- 全站鉴权、四条控制写入路径和三条告警来源属于宽迁移，采用 expand–migrate–contract：先在新深模块旁建立兼容接口，再按调用方批次迁移且保持主线绿色，最后删除旧旁路。
- 现有设备模板、规则模板和告警模板通过适配器导出/导入包资产，避免一次性大迁移；新旧运行路径只允许有明确期限的兼容窗口。
- 任何旧控制旁路和静默实体选源必须在交付就绪版本前移除，不能永久保留为“兼容模式”。

## Testing Decisions

### 主测试缝

- 唯一主测试缝是端到端交付流程：在干净实例中导入固定版本的光储充 EMS 解决方案包，通过公开 API 或 EMS 运行工作台填写站点参数并解决绑定，接入协议模拟设备，执行安装计划，触发实时/历史数据、告警与控制回读，最后运行机器验收清单并断言交付报告。
- 该测试从实施工程师可见边界开始，以交付报告结束，不直接查询数据库或调用内部服务；数据库只作为系统内部实现。
- 主缝先覆盖一台设备、一个读实体实例、一个可控实体实例、一个告警和一个策略动作，再通过数据驱动扩展到 PCS、BMS、PV、EVSE、关口电表及完整参考站点。
- 主缝必须同时验证成功路径和关键失败路径：缺失绑定、多候选绑定、无权限、联锁拒绝、回读超时、告警未现场恢复、Secret 缺失、包不兼容和发布锁不一致。

### 辅助测试缝

- 解决方案清单、参数契约和工作台配置使用契约测试，输入公开文档中的包样例并只断言校验结果、安装计划和错误码。
- 实体绑定解析、三方差异、告警状态机和控制状态机使用确定性单元/属性测试，断言外部状态转换和不变量，不断言内部函数调用。
- REST 与 WebSocket 使用权限矩阵集成测试，逐角色验证允许与拒绝，并验证开发匿名和生产默认拒绝。
- 设备适配器使用协议模拟器契约测试，控制测试必须包括“写成功但回读不一致”。
- 发布流水线验证多架构 manifest、digest 固定、全新数据库迁移、升级迁移、发布锁生成和允许/禁止的回滚路径。
- 前端只测试实施工程师和业主操作员的关键任务流与可访问性，不复制后端 Schema 和权限逻辑。

### 好测试的判断标准

- 只断言用户可见行为、公开契约、状态和证据，不锁定函数名、SQL、内部调用次数或页面 DOM 细节。
- 同一业务不变量尽量只在最高可行测试缝证明；单元测试用于难以从端到端穷举的状态空间和快速故障定位。
- 测试数据不包含真实站点拓扑或凭据，使用公开模拟设备、固定时钟和可重放观测。
- 验收报告不是“测试执行过”的旁证，而是端到端测试直接校验的产品产物。

### 现有先例与迁移

- 现有解析、归一化、聚合和告警逻辑 pytest 继续作为底层安全网，并在语义迁移时改为验证新公开状态和不变量。
- 现有直接访问数据库的验收脚本可用于迁移期间诊断，但不计入配置式交付或四小时试验证据。
- 当前前端没有自动化测试；引入前端测试依赖前需另行批准。首个 tracer bullet 可先以公开 API 端到端测试证明主闭环，并保留人工工作台 smoke，随后再决定最小浏览器自动化方案。

## Out of Scope

- 多租户、一个实例多站点和跨站集中监控。
- 计费、结算、工单、移动应用和客户关系管理。
- 通用拖拽大屏、任意脚本组件和解决方案包内自定义前端代码。
- 自动生成新的协议驱动；首版假设所需 Neuron 驱动和设备模板已存在。
- 完整高级优化调度、AI 预测和电力市场交易；首版仅提供可验收的基础策略。
- 客户现场参数、凭据、真实拓扑和商业实施服务的开源。
- 通过人工修改数据库、复制数据库备份或部署客户专用代码实现交付。
- 把历史告警猜测性重建为新状态机事件。
